## 0. 快速上手：项目脚手架（v1.39.0，优先阅读）

本章面向「按模板管理接口测试项目」的日常使用，是推荐的第一入口；常规的单次接口测试流程见后续章节。**零基础同学直接照 0.0 跟做**；有 Python 基础的看 0.1 起各节即可。

### 0.0 保姆级跟做：从空白电脑到第一个「绿灯」项目

全程只需两条命令 + 浏览器点几下（Windows PowerShell 为例，bash 把 `$env:X = "v"` 换成 `export X=v`）。

**第 0 步：确认电脑上有 Python（一次性）**

```powershell
python --version
```

显示 `Python 3.x` 即可；报错则先去 python.org 安装（安装时勾选 “Add Python to PATH”）。

**第 1 步：安装依赖（只在第一次）**

```powershell
cd D:\path\to\seldom-api-testing
pip install -r requirements.txt
```

**第 2 步：开启脚手架并启动服务**

**以下命令必须同一个 PowerShell 窗口内执行**（环境变量关窗口即失效，属正常现象）：

```powershell
cd D:\path\to\seldom-api-testing
$env:ENABLE_PROJECT_SCAFFOLD = "true"
python -m postman_api_tester
```

看到启动日志后**不要关这个窗口**，它就是服务器。

**第 3 步：打开页面**

浏览器访问 `http://127.0.0.1:5000`，首页会出现「项目脚手架」卡片 → 点「打开项目管理」→ 进入项目列表页（初次为空，正常）。若返回 403：服务启动前没设环境变量，回第 2 步重来。

**第 4 步：创建第一个项目（三步向导）**

1. 列表页点「新建项目」。
2. 选择模板：第一次选「基础接口」卡片即可。
3. 项目信息：名称随便起（如 `我的第一个项目`，不能重名）；执行环境留空（跟随默认环境）；描述可不填。
4. 模板问卷：system 下拉任选一个、module 如 `demo`、owner 填自己名字、**base_url 原样保留默认 `http://127.0.0.1:5000`**（指向本服务自己，保证第一次一定能跑通）→ 点「创建项目」。

成功后自动进入项目详情页，此时项目已自带：1 个集合（健康检查示例接口）、1 张追溯表（示例行）、1 份 README——**创建项目到此完成**。

**第 5 步：点「执行项目」看绿灯（建议）**

详情页「执行与历史」→ 点「执行项目」→ 历史先 `queued`（排队）→ 数秒后 `running` → 最终 **`done`、通过 1、失败 0**；点行内链接可看 HTML 报告。这一步绿了即整条链路打通。

之后要测真实系统：把 base_url 换成被测地址（创建时填，或详情页「编辑项目信息」改），再把自己的 Postman Collection 粘贴进「Collection 集合」即可。

**常见卡点**

| 现象 | 怎么办 |
|------|--------|
| 首页没有脚手架卡片 / 403 | 忘了设环境变量，重开窗口从第 2 步来 |
| 提示「项目名称已存在」 | 换个名称（名称全局唯一） |
| 执行报「无集合可执行」 | 先按 0.4 添加集合 |
| 关掉窗口下次启动又 403 | 正常：环境变量只对当前窗口有效，每次启动前都要重设 |

> 更多细节：0.1 启用与配置参数、0.3~0.7 各步骤说明（含内置模板变量对照表）、0.9 上传自有模板、0.10 常见问题、§14.8 错误码全表。

### 0.1 两步启用

1. 设置环境变量开启总开关：
   - PowerShell：`$env:ENABLE_PROJECT_SCAFFOLD = "true"`
   - bash/Linux：`export ENABLE_PROJECT_SCAFFOLD=true`
2. 启动（或重启）服务后打开 `http://127.0.0.1:5000`：首页出现「项目脚手架」卡片 → 点「打开项目管理」进入 `/projects`。

开关未开启时首页不出现入口，`/projects` 与全部脚手架 API 一律返回 403（`PRJ_100`）；关闭态对既有功能零影响、不创建任何数据目录。

### 0.2 流程一览（30 秒）

```text
模板（内置 3 套，可上传自有）
 └─① 创建项目：填项目信息 + 模板问卷 → 生成项目骨架（初始集合 + 追溯表 + README）
     └─② 挂集合：模板自带初始集合，可在详情页继续粘贴 Postman Collection
         └─③ 一键执行：合并全部集合进入执行队列（与首页手工执行同队列）→ 历史看结果与报告
             └─④ 追溯表：用例编号 ↔ 接口请求对应，转换状态派生自动化率
                 └─⑤ 导出：追溯表 CSV / 整个项目 ZIP
```

### 0.3 第①步：创建项目（`/projects/create`，三步向导）

1. **选择模板**：卡片式选择内置 3 套——
   | 模板 | 适用 | 问卷变量（*为必填） |
   |------|------|---------------------|
   | `tpl_api_basic` 基础接口 | 通用 HTTP 接口回归 | system*（下拉）、module*、owner*、base_url（默认 `http://127.0.0.1:5000`） |
   | `tpl_api_esp` ESP 设备 | 设备类接口 | 同上 + device_name* |
   | `tpl_api_payment` 支付链路 | 支付类接口 | 同上 + channel*（微信支付/支付宝/银联）、merchant_id* |
2. **项目信息**：项目名称必填且**全局唯一**（重复报 409 `PRJ_204`）；「执行环境」下拉来自既有环境配置（`/api/environments`），选定后执行时的 base_url/token 跟随该环境，不选则跟随默认环境；描述可选。
3. **模板问卷**：按模板 schema 动态渲染（必填校验、enum 下拉）→ 点「创建项目」，成功后进入项目详情页。

模板里的 `{{base_url}}` 等占位符会在创建时按你的问卷答案渲染到初始集合中。

### 0.4 第②步：挂载集合（详情页「Collection 集合」）

- 模板已挂好初始集合（含示例接口 + 「状态码 200」断言样板，可直接执行验证链路）。
- 追加集合：填「集合名称」（可选，缺省取 JSON 里的 `info.name`）+ 粘贴 **Postman 导出的 Collection JSON**（必须含 `info` 与 `item`）→「添加集合」。结构不对报 400 `PRJ_401`。
- 集合行可「移除」；单项目集合数有上限（默认 50，超限 409 `PRJ_403`）。

### 0.5 第③步：一键执行与看结果（详情页「执行与历史」）

1. 点「执行项目」：合并项目内全部集合入后台队列（与手工上传执行**同队列**排队），执行历史立刻多出一条 `queued`。
2. 页面自动轮询刷新，状态流转：`queued`（排队）→ `running`（执行中）→ `done`（全部通过）/ `failed`（存在失败）；历史行的「通过/失败」列来自报告统计，点行内链接可看完整 HTML 报告。
3. 服务重启后打开项目详情会自动**对账**：磁盘上已有报告的收敛为终态，报告缺失的标 `unknown`（不会永远挂起）。
4. 常见拒绝：项目无集合 → 409 `PRJ_502`（先回 0.4）；环境不存在或 base_url 非法 → 400 `PRJ_501`（在「编辑项目信息」或环境配置修正）。

### 0.6 第④步：需求追溯表（详情页「需求追溯表」）

- 行字段：用例编号、标题、优先级（如 P0/P1）、转换状态（**待转换/已自动化/手工**）、关联集合与请求 ID（所关联集合被移除后标「悬空」）。
- 「添加行」新增、行内下拉改转换状态 → 点「保存追溯表」**整表一次提交**；并发下他人已保存会提示刷新合并（CAS 409 `PRJ_602`）。
- 表上方统计条实时显示：用例总数 / 已自动化数 / **自动化率**（= 转换状态为「已自动化」的行数占比，保存时由服务端派生）。
- 「导出 CSV」：UTF-8 BOM，Excel 双击打开中文不乱码。

### 0.7 第⑤步：导出（详情页「导出」）

- 「导出项目 ZIP」：打包整个项目（项目信息 + 集合 + 追溯表 + docs），生成后自动经 `/exports/` 链接下载，文件名形如 `proj_<id>_<UTC时间>_project.zip`。

### 0.8 编辑与删除项目

- 「编辑」区：改名称/描述/状态（`active` 进行中 / `completed` 已完成 / `archived` 归档）/执行环境/Base URL 覆盖；保存走乐观锁，若他人已改返回 409 `PRJ_306` 并弹出最新值供合并。
- 「删除项目」：需二次确认；删除项目数据目录（已生成的执行报告仍保留在报告中心）。

### 0.9 （可选）上传自有模板

页面暂未提供上传入口，使用 A15 API（请求体 = 完整 `template.json`；**服务端会重写 id，务必用响应返回的 id** 去建项目）：

```bash
curl -X POST http://127.0.0.1:5000/api/project-templates -H "Content-Type: application/json" -d @template.json
```

用户模板存放于仓库根 `project_templates/`（运行时懒建、不提交 git），与内置模板**同名目录时覆盖内置**；内置模板只读。模板结构说明与示例见 `postman_api_tester/project_templates/api_basic/template.json`（variables 定义问卷、files 定义项目骨架）。

### 0.10 常见问题速查

| 现象 | 原因与处理 |
|------|-----------|
| `/projects` 返回 403 | 总开关未开启，见 0.1（设置后需重启服务） |
| 创建项目提示名称已存在 | 名称全局唯一（409 `PRJ_204`），换个名称 |
| 点执行返回「无集合可执行」 | 未挂集合，回 0.4 添加 |
| 历史长时间停在 queued/running | 队列有任务排队，稍候刷新；重启服务后打开详情页自动对账收敛（报告缺失则 `unknown`） |
| 保存追溯表/编辑信息 409 | 他人已先保存（CAS），按提示刷新后重新编辑（`PRJ_306`/`PRJ_602`） |
| 追溯表 404 `PRJ_601` | 该项目没有 tracing.json（非带追溯文件的模板创建）；改用内置模板重建，或 API 侧先建表 |
| 执行大量连接失败 | 问卷 base_url / 所选环境指向不可达地址，回 0.3/0.8 修正 |
| 模板 id 填了没反应 | A15 会重写模板 id，以**响应返回的 id** 为准（`GET /api/project-templates` 可查全部有效 id） |

> 深度参考：15 个 API 一览与执行对账机制见 §17；完整错误码见 §14.8；命令行/环境变量速查见《快速命令参考.md》§12。

理解方式建议如下：

1. `postman_api_tester/` 负责执行核心与报告服务主实现。

### 2.1 调用路径总览（目录迁移后）

1. 服务启动路径：`python -m postman_api_tester` -> `__main__.py` -> `postman_api_tester/report_server.py`。
2. 路由调用路径：`postman_api_tester/report_server.py` 路由 -> `handlers/*`（入参校验/编排）-> `services/*`（业务能力）-> `report_repository.py` / `report_meta_repository.py` / `report_job_store.py`。
3. 通用支撑路径：`handlers/services` 统一调用 `utils/*`，覆盖 URL 处理、请求构建、响应解析、脱敏与缓存。
4. 执行生成路径：任务入队/重试由 `handlers/job_routes.py` 编排，最终调用 `postman_api_tester.py` 的 `run_postman_tests()` 输出报告三件套。

### 3.3 修改配置文件

编辑文件：`postman_api_tester/config.py`

第一次使用至少关注以下配置：

1. `BASE_URL`：目标环境地址
2. `TOKEN`：认证 token，可留空
3. `REPORT_OUTPUT_DIR`：报告输出目录，可留空
4. `REQUEST_CONNECT_TIMEOUT` / `REQUEST_READ_TIMEOUT`：请求超时
5. `ENABLE_SELECTIVE_RUN`：是否启用“仅执行已选接口”能力
6. `ENABLE_ADHOC_RUN`：是否启用首页“新增接口测试”独立页面入口
7. `ADHOC_MAX_ITEMS` / `ADHOC_DEFAULT_COLLECTION_NAME`：ad-hoc 单次接口上限与默认集合名
8. `REPORT_EXPORT_DEFAULT_SCOPE`：报告导出默认范围（`full` / `report_only`）
9. `REPORT_EXPORT_CHANNEL_MODE`：导出通道模式（`auto` / `legacy` / `stream`）
10. `REPORT_EXPORT_STREAM_THRESHOLD`：自动分流阈值（总接口数 >= 阈值时优先走流式）
11. `ENABLE_RESPONSE_TIME`：是否记录并展示每接口响应时间（默认 `True`）
12. `ENABLE_RETRY_FAILURES`：是否在报告页启用"一键重试失败用例"按钮（默认 `True`）
13. `ENABLE_JUNIT_EXPORT`：是否启用 JUnit XML 导出链接（默认 `True`）
14. `ENABLE_REPORT_LIST_FILTER`：是否启用首页报告列表筛选面板（默认 `True`）
16. `ENABLE_REPORT_ANALYTICS`：是否启用“分析洞察”页签及 analytics 接口（默认 `True`）
17. `REPORT_ANALYTICS_TOP_N_DEFAULT` / `REPORT_ANALYTICS_TOP_N_MAX`：分析 TopN 默认值与上限
18. `REPORT_ANALYTICS_TREND_LIMIT_DEFAULT` / `REPORT_ANALYTICS_TREND_LIMIT_MAX`：趋势序列默认值与上限
19. `REPORT_ANALYTICS_ENABLE_SAMPLES`：是否默认返回错误样本（默认 `False`）
20. `REPORT_ANALYTICS_HISTOGRAM_BUCKETS`：响应时间直方图桶边界（默认 `0,50,100,200,500,1000,3000,5000`）
21. `QUALITY_SCORE_FAILED_PENALTY` / `QUALITY_SCORE_ERROR_PENALTY` / `QUALITY_SCORE_SLOW_PENALTY` / `QUALITY_SCORE_ASSERTION_MISSING_PENALTY`：质量评分扣分阈值
22. `ENABLE_ASSERTIONS`：是否显示 ad-hoc 页面的 JSONPath 断言配置入口（默认 `True`；仅控制 UI 显隐，不影响执行——断言仅在用例配置 `x_assertions` 且安装 jsonpath-ng 时才执行）
23. `ASSERTIONS_ENGINE`：断言引擎类型（默认 `jsonpath`）
24. `ENVIRONMENTS`：多环境配置字典（键为环境名，值为 `{base_url, token}`），通过环境变量 `ENVIRONMENTS_JSON` 注入 JSON 字符串
25. `DEFAULT_ENV_NAME`：默认激活的环境名称
26. `ENABLE_CHECKPOINT_RECOVERY`：是否启用断点恢复（默认 `False`）
27. `CHECKPOINT_FLUSH_EVERY_N`：每执行 N 条写入一次 checkpoint（默认 `1`）
28. `CHECKPOINT_DIR`：checkpoint 目录（空则默认 `reports/checkpoints`）
29. `ENABLE_ASSERTION_STRICT_MODE`：断言引擎异常是否严格判定为 FAILED（默认 `False`）
30. `LOG_LEVEL` / `LOG_FORMAT` / `LOG_SAMPLE_RATE`：日志级别、格式与采样率。
31. `LOG_ALERT_ERROR_WINDOW_SECONDS` / `LOG_ALERT_ERROR_RATE_THRESHOLD_PER_MIN`：ERROR 速率告警窗口与阈值。
32. `ENABLE_CONCURRENT`：是否启用并发执行引擎（默认 `False`）。启用后接口按变量依赖拓扑排序并行执行，`ENABLE_VARIABLE_EXTRACTION=true` 时自动分析依赖分批。
33. `CONCURRENT_WORKERS`：并发执行最大线程数（默认 `10`），仅 `ENABLE_CONCURRENT=true` 时生效。
34. `ENABLE_VARIABLE_FUNCTIONS`：是否启用内置变量函数（`{{timestamp()}}`、`{{uuid()}}` 等，默认 `True`）。关闭后函数表达式原样保留不替换。
35. `GLOBAL_VARIABLES_FILE`：全局变量持久化文件路径（默认 `variables.json`，启用多环境变量管理）。每次执行前自动加载、执行后自动保存提取的变量。设为空字符串可禁用。
36. `GLOBAL_VARIABLES_MAX_COUNT`：全局变量最大数量（默认 `1000`），超出截断。
37. `ENABLE_PRE_REQUEST_SCRIPT`：是否启用 Pre-request 脚本（`x_pre_request` 字段，默认 `False`）。启用后在请求发出前执行 Python 表达式，动态计算变量值。沙箱环境限制仅允许纯计算操作（哈希、编码、时间戳等），禁止文件/网络/系统调用。
38. `ENABLE_ERR_CODE_JUDGMENT`：是否启用 errCode 参与结果判定（默认 `False`，保持旧行为；开启后 errCode 必须匹配 `SUCCESS_ERR_CODES` 中任一值才判定为成功）。
39. `SUCCESS_ERR_CODES`：视为成功的 errCode 值列表，逗号分隔（默认 `"0"`）。
40. `ENABLE_MESSAGE_JUDGMENT`：是否启用 message 参与结果判定（默认 `True`；关闭后不检查 message）。
41. `SUCCESS_MESSAGES`：视为成功的 message 值列表，逗号分隔（默认 `"success"`，空字符串始终视为成功）。
42. `ENABLE_PROJECT_SCAFFOLD`：是否启用项目脚手架（默认 `False`；关闭时 `/projects` 页面与全部脚手架 API 返回 403 `PRJ_100` 且零文件系统痕迹，开启后首页出现「项目脚手架」入口卡片，详见 §0 快速上手与 §17）。
43. `PROJECTS_DIR` / `PROJECT_TEMPLATES_DIR` / `PROJECT_LIST_PAGE_SIZE_DEFAULT` / `PROJECT_MAX_COLLECTIONS` / `PROJECT_TEMPLATE_MAX_BYTES` / `PROJECT_EXECUTION_HISTORY_MAX`：项目脚手架数据目录与调参（默认仓库根 `projects/`、`project_templates/`、20、50、262144、20，见 §17.1）。
示例：

```python
BASE_URL = "http://10.50.11.130:11000"
TOKEN = ""
REPORT_OUTPUT_DIR = r"D:\api-test-reports"
```

配置建议顺序：

1. 先改 `BASE_URL`
2. 再决定 `TOKEN` 是直接填写还是留空自动登录
3. 最后确认 `REPORT_OUTPUT_DIR` 是否要统一输出到固定目录

如需临时覆盖，不必改代码文件，可直接用环境变量：

```powershell
$env:POSTMAN_BASE_URL = "http://10.50.11.130:11000"
$env:POSTMAN_TOKEN = "your_token"
python -m postman_api_tester.postman_api_tester "sample_api_collection.json"
```

### 5.4 请求串联与变量提取（v1.4.0+）

支持从前序接口响应中提取变量，供后续接口使用（典型场景：登录获取 token → 业务接口使用 token）。

**前置条件**：`config.py` 中 `ENABLE_VARIABLE_EXTRACTION = True`

**Collection 配置**：在 Postman Collection 的 `request` 对象中添加 `x_extract` 字段：

```json
{
  “request”: {
    “method”: “POST”,
    “url”: “/api/login”,
    “x_extract”: {
      “auth_token”: “$.data.token”,
      “user_id”: “$.data.userId”,
      “session_id”: “$header.session-id”
    }
  }
}
```

- `$.field.subfield`：从响应 JSON 中提取字段
- `$.array[0].id`：支持数组索引
- `$header.Name`：提取响应头

**使用方式**：

- 后续接口的 URL/headers/body/params 中使用 `{{auth_token}}` 引用提取的变量
- **Web UI**：首页”数据驱动与变量提取”面板中可填写预置变量（JSON 格式），作为串联的初始值

### 5.5 Pre-request 脚本（v1.18.0+）

支持在请求发出前执行 Python 表达式，动态计算变量值（类似 Postman Pre-request Script）。

**两种使用方式**：

#### 方式一：内置变量函数（无需额外配置）

在 Collection JSON 中直接使用 `{{函数名(参数)}}` 语法，与已有变量替换流程一致：

| 函数 | 语法 | 功能 | 示例 |
|------|------|------|------|
| `hmac_sha256` | `{{hmac_sha256(data,key)}}` | HMAC-SHA256 签名（十六进制） | `{{hmac_sha256(order123,secret)}}` → `a3f5...` |
| `md5` | `{{md5(text)}}` | MD5 哈希（十六进制） | `{{md5(password)}}` → `5f4d...` |
| `base64_encode` | `{{base64_encode(text)}}` | Base64 编码 | `{{base64_encode(user:pass)}}` → `dXNlcjpwYXNz` |
| `base64_decode` | `{{base64_decode(text)}}` | Base64 解码 | `{{base64_decode(dXNlcjpwYXNz)}}` → `user:pass` |
| `random_string` | `{{random_string(length,charset)}}` | 随机字符串 | `{{random_string(16,alpha)}}` → `aBcD...` |
| `url_encode` | `{{url_encode(text)}}` | URL 编码 | `{{url_encode(hello world)}}` → `hello%20world` |

`random_string` 的 `charset` 可选值：`alpha`（字母）、`alphanumeric`（字母+数字，默认）、`numeric`（数字）、`hex`（十六进制）。

#### 方式二：x_pre_request 表达式（需启用配置）

**前置条件**：`config.py` 中 `ENABLE_PRE_REQUEST_SCRIPT = True`（默认关闭）

**Collection 配置**：在 `request` 对象中添加 `x_pre_request` 字段：

```json
{
  “request”: {
    “method”: “POST”,
    “url”: “/api/openplatform/upload”,
    “headers”: [
      {“key”: “X-Signature”, “value”: “{{sign}}”},
      {“key”: “X-Timestamp”, “value”: “{{ts}}”}
    ],
    “x_pre_request”: {
      “ts”: “str(int(time.time() * 1000))”,
      “sign”: “hmac.new(b'secret', variables.get('ts', '').encode(), hashlib.sha256).hexdigest()”
    }
  }
}
```

**执行流程**：

1. 执行 `x_pre_request` 中的表达式，计算结果
2. 将结果作为**局部变量**合并到本次请求的变量替换上下文
3. 正常执行变量替换（`{{sign}}`、`{{ts}}` 被替换）
4. 发送请求

**关键特性**：

- **局部变量**：pre-request 设置的变量仅在当前请求内有效，不写入全局 `VariableContext`，不影响并发执行
- **安全沙箱**：限制内置函数 + 白名单模块（`hashlib`/`hmac`/`base64`/`time`/`json`/`re`）+ 危险关键字拦截 + 1 秒超时保护
- **表达式引用**：可通过 `variables.get('name', 'default')` 引用已有变量，通过 `result.get('var', '')` 引用前置表达式结果

**表达式可用模块与变量**：

```python
# 可用模块
hashlib    # MD5, SHA256 等哈希
hmac       # HMAC 签名
base64     # Base64 编解码
time       # 时间戳
json       # JSON 处理
re         # 正则表达式

# 引用已有变量
variables.get('token', '')

# 引用前置表达式结果（按定义顺序）
result.get('step1', '')
```

**典型场景：开放平台动态签名**：

```json
{
  “x_pre_request”: {
    “timestamp”: “str(int(time.time() * 1000))”,
    “nonce”: “random_string(16, 'alphanumeric')”,
    “signature”: “hmac.new(b'app_secret', (variables.get('timestamp', '') + variables.get('nonce', '')).encode(), hashlib.sha256).hexdigest()”
  }
}
```

**Collection 编辑器**：在编辑器中选择接口后切换到 `Pre-request` 标签页，可直接添加/编辑/删除表达式。

### 5.6 Collection 可视化编辑器运行时变量池（v1.5.0+）

Collection 可视化编辑器（`/collection-editor`）内置了**运行时变量池**，用于在手动调试接口时自动管理变量。

**工作原理**：

1. 在编辑器中选中接口 A，配置 `x_extract` 提取规则
2. 点击 **Send** 发送请求，系统从响应中提取值并存入变量池
3. 选中接口 B，其 body/URL/headers 中的 `{{变量名}}` 会自动用变量池中的值替换
4. 执行整个 Collection 时，变量池中的值会作为 `initial_variables` 传给后端

**示例流程**：

导入 `前厅查询接口test01.json`，包含两个接口：

```
接口 1：部门列表
  POST http://10.50.11.120:9001/api/mer/department/queryPage
  x_extract: {“merchantid”: “$.data.list[0].merchantId”}

接口 2：企业员工
  POST http://10.50.11.120:9001/api/us/employee/query/page
  body: {“merchantId”: {{merchantid}}, ...}
```

操作步骤：

1. 导入 JSON 文件
2. 选中”部门列表”，点击 Send → 响应返回后，变量池自动写入 `{merchantid: “2021040701”}`
3. 状态栏显示：`请求完成 200 ... 运行时变量 1 个`
4. 选中”企业员工”，点击 Send → `{{merchantid}}` 被自动替换为 `”2021040701”`，接口正常返回 200

**🧹 清除变量按钮**：

点击编辑器顶部”🧹 清除变量”按钮，会清空运行时变量池。适用于以下场景：

| 场景 | 说明 |
|------|------|
| 重新测试 | 想让接口 1 重新提取最新值，需先清除再重发 |
| 切换测试数据 | 清除旧变量，避免污染新一轮测试 |
| 变量值过期 | 提取的值已失效，需重新提取 |
| 测试无变量行为 | 验证接口在缺少变量时的表现 |

**注意**：

- “清除变量”只清除运行时提取的变量，不影响 Collection 的预置变量（`variables` 字段）
- 执行整个 Collection 时，预置变量 + 运行时变量池合并后作为初始变量传给后端
- 拖拽调整接口顺序后，执行顺序与页面显示一致

### 5.7 全局变量与多环境变量管理（v1.12.0+）

#### 5.6.1 功能概述

全局变量支持**多环境作用域**管理，变量存储分为两类：

- **全局共享变量（shared）**：跨所有环境生效，适用于通用的 token、app_version 等
- **环境变量（environments）**：按环境名分组，适用于不同环境的 base_url、db_host 等

变量数据持久化在 `GLOBAL_VARIABLES_FILE` 配置的 JSON 文件中（默认 `variables.json`），格式为 version 2：

```json
{
  "version": 2,
  "updated_at": "2026-06-17T10:30:00",
  "shared": {"auth_token": "eyJhbG..."},
  "env_list": ["默认环境", "生产环境", "测试环境"],
  "environments": {
    "默认环境": {},
    "生产环境": {"base_url": "http://10.50.11.130:11000"},
    "测试环境": {"base_url": "http://10.50.11.120:8090"}
  }
}
```

#### 5.6.2 变量覆盖顺序（重要）

当全局共享变量和环境变量中存在**同名变量**时，按以下优先级决定最终生效的值（从高到低）：

| 优先级 | 来源 | 说明 |
|--------|------|------|
| 最高 | `initial_variables` | 执行时传入的预置变量 / Collection 预置变量 / 运行时提取变量 |
| 中 | `environments[env_name]` | 所选环境的变量（如"生产环境"的 base_url） |
| 最低 | `shared` | 全局共享变量（如通用的 auth_token） |

**规则：同名 key 后者覆盖前者。** 例如：

```
shared 中有:        base_url = "http://default:8080"
测试环境中有:        base_url = "http://test:8090"
执行时选择"测试环境" → 最终 base_url = "http://test:8090"（环境覆盖 shared）

shared 中有:        auth_token = "shared_token"
测试环境中没有 auth_token
执行时选择"测试环境" → 最终 auth_token = "shared_token"（继承 shared）
```

#### 5.6.3 设置面板操作

首页右上角**齿轮按钮**打开环境变量设置面板，包含 3 个 Tab：

1. **全局变量 Tab**：管理 shared 变量，每行可直接编辑名称和值，底部空白行输入后自动添加新变量
2. **环境变量 Tab**：选择环境后管理该环境的变量，支持添加/删除环境
3. **变量函数 Tab**：查看 6 个内置变量函数的语法和示例（`timestamp()`、`uuid()`、`random_int()` 等）

**交互说明**：
- 变量值默认脱敏显示（`***`），点击"👁 显示值"按钮切换明文/脱敏
- 编辑已有变量：直接点击名称或值输入框修改，失焦（blur）自动保存
- 重命名变量：修改名称后保存，系统自动删除旧 key 并创建新 key
- 添加变量：在底部空白行输入名称和值，失焦自动创建
- 快捷键：Enter 跳到下一个输入框，Escape 撤销修改

#### 5.6.4 Collection 编辑器集成

可视化编辑器（`/collection-editor`）自动加载全局/环境变量：

- 编辑器顶部显示环境选择下拉框和已合并变量数提示
- 编辑接口时，URL/Headers/Body 中的 `{{变量名}}` 可使用全局和环境变量
- 变量自动补全（输入 `{{`）显示来源标签："全局"、"环境"、"预置"、"运行时"
- 导出 JSON 时，全局/环境变量自动嵌入到 `collection_info.variables` 中，供其他工具复用
- 执行 Collection 时，全局/环境变量作为 `initial_variables` 传递给后端

编辑器中的变量合并顺序（从高到低）：运行时变量 > Collection 预置变量 > 环境变量 > 全局共享变量。

### 5.7 Collection 编辑器断言页签（v1.37.15+）

可视化编辑器（`/collection-editor`）选择接口后可切换到 **断言** 页签，为该接口配置 JSONPath 断言（页签随 `ENABLE_ASSERTIONS` 配置显隐，默认开启）。

**操作步骤**：

1. 点击「+ 添加断言规则」，填写 JSONPath（如 `$.errCode`）并选择操作符
2. 操作符支持 13 种：eq/ne/gt/lt/gte/lte/contains/regex/length_eq/type/schema/exists/not_exists
3. `expected` 填 JSON 字面量：数字 `0`、布尔 `true`、带引号字符串 `"ok"`、对象 `{"a": 1}`；选择 `exists`/`not_exists` 时该输入框自动禁用
4. 保存/导出时断言写入 Collection 的 `request.x_assertions` 字段，随 Collection 执行

**页面结构（v1.38.2 起归并两卡片；存储仍为四键各自数组，行为不变）**：

1. **本接口规则**：聚合该接口的判定规则（`x_judgment_rules`）与断言（`x_assertions`），行前以「判定」（橙）/「断言」（绿）徽标区分阶段；添加时通过「阶段」下拉选择新增为判定或断言。卡片内含：
   - **成功标准** radio 快捷开关：「内置业务判定」（默认，两 `x_enable_*` 置继承）⇄「断言接管」（等效把 errCode/message 判定双双强制关闭）；切到接管时若自有与集合共享断言皆空会弹确认（判定规则不计入——双关时判定一并跳过）。
   - **豁免集合共享规则** 勾选（`x_skip_shared_assertions`）：本接口不执行集合共享判定与共享断言。
   - **⚙ 精细控制**（折叠）：errCode / message 判定各自的「继承 / 强制开启 / 强制关闭」三态，与成功标准 radio 操作同一对字段（双「强制关闭」即接管态）。
2. **集合共享规则**：聚合同一接口视图下的 Collection 根级共享判定（`x_shared_judgment_rules`）与共享断言（`x_shared_assertions`），同样徽标区分、阶段下拉添加；对集合内全部未豁免接口生效。

执行语义不变：内置判定（状态码/errCode/message）→ 自定义判定规则（任务 → 共享 → 接口自有，任一失败短路断言）→ 断言（共享在前、自有在后）。任务级「关闭一级判定」勾选优先于接口级设置。

**共享断言接管一级判定的典型用法**：将接口的「成功标准」切到「断言接管」（或整任务勾选「关闭一级判定」）后，用共享断言 `$.errCode eq 0` 承担成功判定职责；对预期返回业务错误码的异常接口勾选「豁免集合共享规则」并依赖其自有断言判定。
**自定义一级判定规则（v1.37.22）**：在本接口规则卡片通过「阶段=判定」添加 `request.x_judgment_rules`（与断言同结构、同 13 操作符）。内置判定（状态码/errCode/message）通过后评估，任一失败即判 FAILED 且**不再执行断言**。「关闭一级判定」的任一开关（任务级勾选 / 接口级双强制关闭或接管态 / 全局 config 双 False）会**联动关闭自定义规则**；状态码兜底不可关闭。

**任务级入口（v1.37.23）**：无需进编辑器，首页「判定条件配置」区即可添加自定义判定规则（path/op/expected 行编辑），点击「上传并执行」时随任务提交，**对本次执行的每个接口生效**；与接口级规则合并评估，任务级在前、接口级在后（AND）。注意：勾选「关闭一级判定」时任务级规则一并不执行；规则仅对本次执行生效，不落盘到 Collection。JSON/API 通道等价写法：payload 的 `judgment_config.custom_rules`（数组）。

**集合级共享判定（v1.38.1）**：想让统一业务判定（如 `$.code eq 0`）**持久跟着 Collection 走**（免每次任务重配，CLI 直接执行也生效），在可视化编辑器「集合共享规则」卡片的「判定」徽标下配置根级 `x_shared_judgment_rules`，对集合内全部接口的判定层生效；合并顺序为**任务级 → 集合共享 → 接口自有**（AND）。个别接口不受约束：勾选该接口的「豁免集合共享规则」（与共享断言共用同一豁免开关）。同样受「关闭一级判定」联动：关闭后共享判定一并跳过（状态码兜底保留）。

**判定 vs 断言对照表**：

| 维度 | 一级判定（内置 + 自定义规则） | 断言（自有 + 集合共享） |
|---|---|---|
| 执行时机 | 断言之前 | 判定全部通过之后 |
| 失败效果 | FAILED，短路断言 | FAILED（判定结论不受影响） |
| 关闭方式 | 任务级勾选 / 接口级三态 / 全局 config（自定义规则联动失效；状态码不可关） | 不配置即不执行 |
| 规则结构 | `{path, op, expected}`（同一归一化口径） | 同左 |
| 适用建议 | 业务成败门槛（如 errCode 白名单之外的字段级门槛） | 响应内容正确性校验、关闭判定后接管成败 |


**判定时机**：断言在响应通过结果判定（errCode/message）之后逐条校验，任一失败则该用例判为 FAILED。

**已知边界**：

- `expected` 不支持 `{{变量}}` 替换（变量替换跳过 `x_assertions` 字段）
- 存量含 `x_assertions` 的集合自 v1.37.14 起断言真正执行（此前被 parser 静默丢弃），个别用例可能 PASSED→FAILED

### 5.8 请求/响应对比视图（v1.20.8+）

#### 5.8.1 功能概述

Collection 编辑器支持**并排对比两次请求**的完整报文（URL、Headers、Body、Response），高亮差异部分，便于排查接口行为变化。

**适用场景**：
- 回归测试前后对比（发版前 vs 发版后）
- 不同参数配置下的请求/响应差异分析
- 接口性能对比（高峰期 vs 低峰期耗时）
- 调试时对比预期与实际响应

#### 5.8.2 操作步骤

**第一步：发送多次请求**

1. 在 Collection 编辑器中选择任意接口
2. 点击 **Send** 按钮发送请求
3. 重复 2 次以上（可修改参数后再次发送）

每次请求成功后，系统自动保存到对比历史（最多 20 条，FIFO 淘汰）。

**第二步：打开对比历史面板**

1. 在响应面板顶部工具栏，点击 **"对比历史"** 按钮（双箭头图标）
2. 下拉面板显示最近 20 次请求记录
3. 每条记录显示：时间 | 状态码 | URL（截断）

**第三步：选择 2 条记录**

1. 点击记录左侧复选框，勾选第 1 条
2. 再勾选第 2 条（最多选 2 条）
3. 选满 2 条后，顶部出现 **"开始对比"** 按钮

**第四步：查看对比结果**

1. 点击 **"开始对比"**，弹出全屏对比模态框
2. 左右两栏并排显示差异
3. 顶部 6 个 Tab 切换对比维度：
   - **URL & Method**：请求方法和地址
   - **Request Headers**：请求头
   - **Request Body**：请求体
   - **Response Status**：响应状态码和耗时
   - **Response Headers**：响应头
   - **Response Body**：响应体（最常用）

#### 5.8.3 差异高亮说明

| 颜色 | 含义 | 示例 |
|------|------|------|
| 🟢 绿色背景 | 新增行（仅在右侧） | 新接口返回了额外字段 |
| 🔴 红色背景 | 删除行（仅在左侧） | 旧接口有但新接口没有的字段 |
| ⚪ 无背景 | 未变行（两侧相同） | 相同的数据 |

**差异统计栏**：底部显示 `+N 行新增`、`-N 行删除`、`N 行未变`。

#### 5.8.4 使用场景示例

**场景 1：回归测试前后对比**

```
操作：
1. 发版前：发送 GET /api/users → 保存历史
2. 发版后：再次发送 GET /api/users → 保存历史
3. 对比两次 Response Body

预期结果：
- 绿色高亮：新增的用户字段
- 红色高亮：被移除的字段
- 无高亮：未变化的数据
```

**场景 2：不同参数对比**

```
操作：
1. 发送 POST /api/search，body: {"keyword": "测试"}
2. 修改 body: {"keyword": "生产"}，再次发送
3. 对比两次 Request Body 和 Response Body

预期结果：
- Request Body 红色："测试"
- Request Body 绿色："生产"
- Response Body 显示不同搜索结果
```

**场景 3：接口性能对比**

```
操作：
1. 高峰期发送请求，记录耗时 1500ms
2. 低峰期发送相同请求，记录耗时 300ms
3. 对比 Response Status Tab

预期结果：
- 左侧：1500ms（红色高亮）
- 右侧：300ms（绿色高亮）
```

#### 5.8.5 快捷操作

| 操作 | 方式 |
|------|------|
| 关闭对比视图 | 点击右上角 × 或按 **ESC** 键 |
| 清除选择 | 点击对比历史面板的"清除选择"按钮 |
| 切换 Tab | 点击顶部 Tab 标签 |

#### 5.8.6 注意事项与限制

1. **历史记录上限**：最多保存 20 条，超出后自动删除最旧的（FIFO 淘汰）
2. **大响应降级**：响应体 > 1MB 时自动截断，> 10000 行时使用简单对比（避免卡顿）
3. **二进制响应**：图片/PDF 等二进制内容不展示 diff，仅显示元信息
4. **页面刷新清空**：历史记录保存在内存中，刷新页面后清空
5. **最多选 2 条**：系统限制只能选 2 条记录进行对比

#### 5.8.7 常见问题

**Q1: 对比历史按钮点不了？**

A: 需要先发送至少 1 次请求，历史记录为空时按钮置灰。

**Q2: 只能选 1 条，无法选第 2 条？**

A: 系统限制最多选 2 条。如需换选，先点击"清除选择"再重新勾选。

**Q3: 对比视图显示空白？**

A: 可能是响应体为空或二进制内容。切换到其他 Tab（如 Headers）查看。

**Q4: 差异高亮不准确？**

A: 大文本（>10000 行）会降级为简单逐行对比，精度略低。建议缩小响应范围或分页查询。

**Q5: 如何对比不同接口的请求？**

A: 可以。对比历史保存所有接口的请求记录，勾选任意 2 条即可对比。

**Q6: 历史记录会保存到下次启动吗？**

A: 不会。历史记录仅保存在浏览器内存中，刷新页面或关闭浏览器后清空。如需持久化对比，可手动复制响应内容到外部工具。

**Q7: 对比模态框太大，能否调整大小？**

A: 当前版本为全屏模态框，暂不支持调整大小。按 ESC 键可快速关闭。

### 7.1.1 服务进程管理（查找、停止与重启）

当页面返回 404、行为不符合预期，或修改代码后需要生效时，通常需要停止旧进程并重启服务。

#### 1. 确认服务是否在运行

打开浏览器访问 `http://127.0.0.1:5000`，如果返回 `Not Found` 或页面内容与预期不符，可能是旧进程仍在运行。

也可用命令行快速验证：

```bash
curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:5000/
```

返回 `200` 表示服务正常响应；`404` 或其他状态码需进一步排查。

#### 2. 查找占用 5000 端口的进程

```bash
# Windows（Git Bash / MSYS2 环境）
netstat -ano | grep ":5000.*LISTEN"
```

输出示例：

```
TCP    0.0.0.0:5000    0.0.0.0:0    LISTENING    48500
```

最后一列即为进程 PID（上例为 `48500`）。

如果 `grep` 不方便，也可以用 PowerShell（需管理员权限或调整执行策略）：

```powershell
Get-NetTCPConnection -LocalPort 5000 -State Listen | Select-Object LocalPort, OwningProcess, State
```

#### 3. 停止旧进程

查到 PID 后，逐个终止：

```bash
taskkill //F //PID <PID>
```

示例：

```bash
taskkill //F //PID 48500
```

如果同一端口有多个 Python 进程（常见于多次启动未正常退出），需要逐个终止，直到 `netstat` 不再显示 `LISTENING` 状态：

```bash
netstat -ano | grep ":5000.*LISTEN"
# 如果输出为空，说明端口已释放
```

#### 4. 重新启动服务

```bash
cd d:\tangzk\py\seldom-api-testing
python -m postman_api_tester
```

启动成功后终端会显示：

```
 * Running on http://127.0.0.1:5000/
```

此时浏览器刷新 `http://127.0.0.1:5000` 即可正常访问。

#### 5. 常见问题

| 现象 | 原因 | 处理方式 |
|------|------|---------|
| 访问首页返回 404 | 旧进程仍在运行，未加载最新代码 | 按上述步骤终止旧进程后重启 |
| 启动时报 `Address already in use` | 端口被其他进程占用 | 先查找并终止占用端口的进程 |
| 终端无输出且浏览器无响应 | 服务未成功启动 | 检查 `requirements.txt` 依赖是否已安装 |
| 局域网其他机器无法访问 | 防火墙未放通 5000 端口 | 执行 `allow_report_server_firewall.ps1` |

### 7.2.2 full 与 report_only 的区别和使用方法（重点）

两种导出范围都遵循同一总规则：

1. 先基于源 Collection 生成导出内容。
2. 再合并人工用例（`manual_cases`）。
3. 最后剔除已排除项（`manual_exclusions`）。

核心差异仅在“步骤 1 的基底范围”不同：

| 维度 | `full`（全量导出） | `report_only`（导出本次报告接口） |
|---|---|---|
| 基底接口范围 | 源 Collection 全部接口 | 仅本次报告实际执行到的接口（按 `item_path` 裁剪） |
| 是否保留未执行接口 | 保留 | 不保留 |
| 导出文件典型用途 | 保留完整集合做后续回归 | 产出最小复现集合用于问题定位/复测 |
| 与 `full` 何时相同 | - | 当“本次报告接口集合 == 源 Collection 接口集合”时，两者内容会相同 |

什么时候两者会不同：

1. 本次执行是“仅执行已选接口”或其它非全量场景。
2. 源 Collection 后续新增了接口，但本次报告未覆盖到。
3. 本次报告来自局部执行（例如临时挑选接口）而非全量回归。

什么时候两者看起来一样（这是正常现象）：

1. 本次报告本身就是对该源 Collection 的全量执行。
2. 源 Collection 仅包含本次报告那批接口。

如何选择（实操建议）：

1. 需要“完整回归包”或希望继续覆盖未执行接口：选 `full`。
2. 需要“最小复现包”给开发/联调快速复测：选 `report_only`。
3. 不确定时先选 `full`；若目标是复现本次问题再切 `report_only`。

页面使用步骤：

1. 进入单报告“数据视图”页面，点击“导出最新 JSON”。
2. 在下拉中选择导出范围：`全量导出` 或 `导出本次报告接口`。
3. 如需保留认证头再勾选“导出包含 token/authorization”。
4. 点击导出后，弹窗会显示导出范围与数量信息；若两种范围等价会明确提示原因。

导出通道策略说明：

1. `auto`：总接口数达到阈值时优先走 `/api/export-collection-stream`；若流式失败自动回退 `/api/export-collection`。
2. `legacy`：强制走 `/api/export-collection`，适合对比历史链路或排查流式问题。
3. `stream`：强制走 `/api/export-collection-stream`，适合验证流式链路。

### 7.2.1 直接新增接口测试（ad-hoc）使用说明

适用场景：

1. 只想快速验证 1~N 条接口，不想先整理完整 Collection。
2. 联调期需要临时录入 headers/params/body 并直接生成标准报告。

操作步骤：

1. 启动 `python -m postman_api_tester` 并打开首页。
2. 点击首页“打开新增接口测试页”，进入独立页面后填写 `collection_name`、`base_url`、`token`、`report_name`、`results_per_page`（均可按需填写）。
3. 新增接口行并录入 `name`、`folder`、`method`、`url`、`headers`、`params`、`body_mode`、`body_data`。
4. 点击执行后，前端调用 `/api/run-ad-hoc-tests`，后端会生成临时 Collection 并复用现有任务队列执行。
5. 继续沿用现有任务状态轮询与报告查看流程，执行完成后进入新报告页。

输入约束：

1. `cases` 至少 1 条，且总数不得超过 `postman_api_tester/config.py` 中 `ADHOC_MAX_ITEMS`。
2. `url` 支持三种形态：绝对 `http/https`、`{{baseUrl}}/...` 或 `{{base_url}}/...`、以及配合 `base_url` 的相对路径。
3. `body_mode` 支持 `none/raw/urlencoded/formdata/graphql/binary`，与既有导出/重试/代理请求语义保持一致。
4. 使用变量 URL 或相对路径时，必须提供合法 `base_url`；`base_url` 与绝对 URL 均只允许 `http/https`。
5. ad-hoc 任务会在 `uploaded_collections/` 中生成临时 JSON 文件，报告产物仍按标准三件套落在报告目录。

### 7.3 报告目录一致性

报告中心读取目录优先级：

1. `POSTMAN_REPORTS_DIR`
2. `REPORTS_DIR`
3. `postman_api_tester/config.py` 中 `REPORT_OUTPUT_DIR`
4. 默认 `项目根目录/reports/`

健康检查补充：

1. `GET /health` 仍保留 `status` 与 `timestamp`。
2. 当启用日志告警策略时，返回体扩展 `log_alert` 字段（ERROR 速率快照与阈值对比结果）。

按此规则可确保“测试执行输出目录”和“报告中心读取目录”一致。

### 7.4 防火墙说明

如果其他机器无法访问，但本机可以访问，请检查 Windows 防火墙是否允许 Python 或 5000 端口的入站访问。

推荐直接使用项目根目录脚本一键放通：

```powershell
cd d:\tangzk\py\seldom-api-testing
powershell -ExecutionPolicy Bypass -File .\allow_report_server_firewall.ps1
```

说明：

1. 脚本会自动申请管理员权限。
2. 默认放通 TCP 5000 端口，规则名为 `Postman Report Server 5000`。
3. 执行完成后，同局域网可通过 `http://你的局域网IP:5000` 访问报告中心。

```powershell
New-NetFirewallRule -DisplayName "Postman Report Server 5000" -Direction Inbound -Action Allow -Protocol TCP -LocalPort 5000
```

## 9. 故障排查

- 未登录/401：优先确认 token 来源和优先级
- URL错误：检查 base_url 覆盖逻辑
- 接口超时：确认网络、防火墙、目标服务健康状态
- message 中出现“数据库反馈”：优先按提示检查连接、权限、SQL 方言、schema 或字符集问题
- 导出后二次导入出现“预览 2 条但执行 1 条”：升级至当前版本后已修复；根因是旧逻辑仅按 `request.url.path` 解析，未覆盖仅 `raw` 的 URL 结构
- 导出后二次导入后人工用例请求体显示“无”或执行失败：当前版本已修复；根因是旧导出链路写入人工用例时只保留 method/url，未带出 headers/params/body
- 人工用例新增后显示在列表最后：当前版本已修复；读取人工用例时不再为缺失 `created_at` 的旧数据临时补当前时间，避免排序漂移
- 数据视图搜索对人工用例无效：当前版本已修复；搜索词/状态/排除开关已同步作用于人工用例列表
- 报告为空：确认 JSON 是否包含 item/request 结构
- 局域网不可访问：检查 `python -m postman_api_tester` 是否已启动，以及防火墙是否放通 5000 端口
- 无法对比历史报告：确认 `reports/` 下同时存在 `postman_report_*.html` 与对应的 `postman_report_*_meta.json`

## 10.1 缓存命中验证

当需要验证服务端缓存是否生效时，可使用 ad-hoc 页面的**重复执行**功能：

### 操作步骤

1. 进入报告中心，点击"新增接口测试"（ad-hoc 页面）。
2. 录入查询接口信息（名称、方法、URL 等）。
3. 在"重复次数"字段输入执行次数（1~10，默认 1）。建议设为 5。
4. 点击"加入列表"，然后执行任务。
5. 打开报告页面，查看结果：
   - 接口名称后显示 `×1/5`、`×2/5` 等重复序号徽标
   - 第 1 次为缓存未命中（miss），后续为缓存命中（hit）
   - 对比第 1 次与后续的 `耗时(ms)` 列即可判断缓存是否生效

### 判断标准

- **缓存生效**：第 1 次耗时 ≥ 200ms，后续耗时 ≤ 20ms，加速比 ≥ 10x
- **缓存未生效**：各次耗时相近，无明显差异

### 注意事项

- 重复执行仅对**同一查询接口**有效，适用于 GET 查询类接口
- 缓存验证后建议将重复次数恢复为 1，避免常规测试增加耗时

- 采用部分匹配：只要页面任意位置包含该文本即通过

#### 15.2.4 assert_element_exists — 语义化选择器断言

验证指定角色+文字的元素存在。使用 `role:text` 格式的语义化选择器，比纯 CSS 选择器更直观，比纯文本匹配更精确。

**使用方式**：在"选择器"字段填写 `role:文字`，"值"字段留空。

**示例：确认"查看订单"按钮存在**

| 字段 | 值 |
|------|---|
| 操作 | `assert_element_exists` |
| 选择器 | `button:查看订单` |
| 值 | 留空 |
| 描述 | 验证页面存在"查看订单"按钮 |

**语法格式**：

```
button:文字      # 按钮
link:文字        # 链接
heading:文字     # 标题（h1-h6）
label:文字       # 标签
menuitem:文字    # 菜单项
tab:文字         # 标签页
checkbox:文字    # 复选框
radio:文字       # 单选框
option:文字      # 下拉选项
textbox:文字     # 文本输入框
dialog:文字      # 对话框
alert:文字       # 警告提示
tooltip:文字     # 工具提示
```

**完整角色列表**（28 种 ARIA 角色）：

| 类别 | 角色 |
|------|------|
| 交互控件 | `button`、`checkbox`、`combobox`、`radio`、`slider`、`spinbutton`、`switch`、`textbox`、`searchbox` |
| 容器 | `dialog`、`alert`、`menu`、`tabpanel`、`tooltip`、`progressbar`、`separator`、`scrollbar` |
| 菜单项 | `menuitem`、`menuitemcheckbox`、`menuitemradio`、`option`、`listitem`、`treeitem` |
| 导航 | `link`、`tab`、`heading`、`label` |
| 数据展示 | `gridcell` |

**常用示例**：

| 选择器 | 说明 |
|--------|------|
| `button:提交` | 验证"提交"按钮存在 |
| `link:首页` | 验证"首页"链接存在 |
| `heading:系统设置` | 验证"系统设置"标题存在 |
| `tab:订单管理` | 验证"订单管理"标签页存在 |
| `menuitem:退出登录` | 验证"退出登录"菜单项存在 |
| `option:待处理` | 验证下拉框有"待处理"选项 |
| `dialog:确认删除` | 验证弹出"确认删除"对话框 |

**使用场景**：
- 验证按钮、链接等交互元素存在
- 检查菜单项、标签页等导航元素
- 确认对话框、提示框弹出
- 验证下拉选项可用

**注意事项**：
- 格式为 `role:文字`，冒号必须是英文冒号
- 角色名不区分大小写（`BUTTON:提交` 和 `button:提交` 等效）
- 如果文字中包含冒号，会被正确保留（如 `label:时间: 10:30`）

### 15.10 注意事项

1. **选择器唯一性**：确保选择器能唯一定位目标元素，否则可能断言错误的元素
2. **等待时间**：断言会自动等待元素出现，超时时间可在执行设置中配置
3. **部分匹配**：`assert_text`、`assert_text_exists`、`assert_url`、`assert_title` 等使用部分匹配（包含即可）
3.1. **简化选择器**：如果只需确认页面某处出现特定文字，优先使用 `assert_text_exists`（无需选择器，直接填写文字即可）
4. **精确匹配**：`assert_value`、`assert_attribute`、`assert_css` 使用精确匹配
5. **大小写敏感**：文本匹配默认大小写敏感
6. **可见性判断**：`assert_visible` 要求元素在视口内且未被隐藏
7. **对话框处理**：`assert_dialog` 会自动关闭对话框，无需手动处理
8. **Cookie 作用域**：`assert_cookie` 检查当前页面上下文的所有 Cookie

### 15.11 UI 自愈（v1.38.0+，仅无头执行）

页面改版导致选择器腐化时，无头引擎可在元素定位超时后**自动修复选择器**继续执行，减少因 UI 微调导致的大面积误报失败。

**开启方式**（环境变量，默认全部关闭）：

| 变量 | 默认 | 说明 |
|---|---|---|
| `UI_SELF_HEALING_ENABLED` | `false` | 自愈总开关 |
| `UI_HEALING_CONFIDENCE` | `70` | 采纳置信阈值（10~100 整数百分比，低于则拒绝） |
| `UI_HEALING_MAX_PER_CASE` | `5` | 单用例自愈尝试熔断上限（1~50） |

**修复策略**（按置信度从高到低，首个通过采纳校验即停止）：

1. `test_id`（95 分）：录制时快照的 `data-testid` 重新定位
2. `role_text`（85 分）：角色（button/link 等）+ 无障碍名/文字定位
3. `text`（75 分）：可见文字定位
4. `xpath_lcs`（连续分）：录制 xpath 与页面候选结构相似度

采纳前强制校验「唯一匹配 + 可见」；宁漏勿误修——元素仍在位但定位失败、或探测异常时一律不自愈。

**边界与注意**：
- **仅无头执行模式支持**；浏览器回放模式不做自愈（引擎层红线）。
- `assert_*` 断言步骤不自愈——断言失败必须真实暴露，不能"修好"。
- 自愈只在本次运行期生效，**不会改写用例里的选择器**；报告徽章提示的「原 → 新」确认后请自行到编辑器修正并重新录制。
- 同一步骤最多自愈一次；单用例尝试数达到熔断上限后，后续失败不再尝试。

**报告识别**：步骤行显示「已自愈」徽章（悬停可见 原选择器 → 新选择器 与策略/置信度），详情页有"自愈步骤"统计卡，报告列表页显示「自愈 N」徽标。

**排查**：中央日志与 `logs/headless/exec_{job_id}.jsonl` 双通道记录 `self_healing.*` 事件（attempt/rejected/healed/healed_then_failed/capped/probe_error），见《日志事件字典》2.16。

## 16. 服务器部署（Linux：systemd + nginx 反向代理）

### 16.1 适用场景

将报告中心常驻部署到内网服务器，团队通过浏览器统一使用：上传 Collection 执行、ad-hoc 测试、查看报告/分析/重试/导出。UI 录制（局域网代理）功能依赖本机浏览器会话，建议仍在本机操作，服务器承担回放与无头执行。

### 16.2 安装与运行

```bash
git clone <仓库地址> /opt/seldom-api-testing
cd /opt/seldom-api-testing
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt   # v1.37.13 起 requirements 已含 waitress（生产 WSGI）
```

关键环境变量（均可覆盖 `config.py` 默认值，无需改代码）：

| 变量 | 说明 | 部署建议值 |
|---|---|---|
| `POSTMAN_BASE_URL` | 被测系统默认地址 | 按实际环境设置（默认值是内网示例，必须覆盖） |
| `POSTMAN_TOKEN` | 接口 Token | 留空则走自动登录（auth.py） |

### 16.3 systemd 常驻

```ini
# /etc/systemd/system/api-tester.service
[Unit]
Description=Postman API 测试报告中心

[Service]

```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now api-tester
journalctl -u api-tester -f          # 查看运行日志
```

> **必须单进程部署**：任务队列（RUN_JOBS）为进程内内存态，waitress 单进程多线程即为正确形态；**不要**使用 gunicorn 多 worker 或同时跑多个实例，否则任务状态与轮询会割裂。

### 16.4 nginx 反向代理 + BasicAuth（推荐，应用层当前无登录）

```bash
sudo yum install -y httpd-tools      # 或 apt install apache2-utils
sudo htpasswd -c /etc/nginx/.apitest_passwd <用户名>
```

```nginx
# /etc/nginx/conf.d/api-tester.conf
server {
    listen 80;
    server_name api-tester.internal;

    auth_basic "API 测试报告中心";
    auth_basic_user_file /etc/nginx/.apitest_passwd;

    client_max_body_size 50m;        # Collection / 数据文件上传
    proxy_read_timeout 300s;         # 长任务轮询与 UI 代理留余量

    location / {
        proxy_pass http://127.0.0.1:5000;
        proxy_set_header Host $host;             # 代理 URL 改写依赖 Host，必须传递
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

```bash
sudo nginx -t && sudo systemctl reload nginx
```

> 安全底线：应用本身对全部端点（含删除报告、执行任务、请求代理）**无鉴权**，部署时至少满足"nginx BasicAuth"与"防火墙/安全组限内网网段"二者之一。UI 代理目标需在服务器上另行配置 `UI_PROXY_ALLOWED_HOSTS` 白名单。

## 17. 项目脚手架·参考（v1.39.0）

> 操作流程见本手册开头 §0 快速上手（启用 → 创建 → 挂集合 → 执行 → 追溯 → 导出）；本节仅保留配置调参、执行对账机制、API 清单与冒烟等深度内容。错误码详表见 §14.8，命令行速查见《快速命令参考.md》§12。

### 17.1 配置调参

| 环境变量 | 默认 | 用途 |
|----------|------|------|
| `ENABLE_PROJECT_SCAFFOLD` | `false` | 总开关；关闭时页面/API 403 `PRJ_100`、零文件系统痕迹 |
| `PROJECTS_DIR` | 仓库根 `projects/` | 项目数据根（懒建，不提交 git） |
| `PROJECT_TEMPLATES_DIR` | 仓库根 `project_templates/` | 用户模板根（同名目录覆盖内置模板） |
| `PROJECT_LIST_PAGE_SIZE_DEFAULT` | 20（1~100） | 列表默认分页大小 |
| `PROJECT_MAX_COLLECTIONS` | 50（1~500） | 单项目集合数上限 |
| `PROJECT_TEMPLATE_MAX_BYTES` | 262144（1KB~1MB） | 模板文件体积上限（A15 声明期校验） |
| `PROJECT_EXECUTION_HISTORY_MAX` | 20（1~200） | 执行历史保留条数（超出截断最旧） |

### 17.2 执行链与懒对账（进阶）

- 执行 = 合并项目内全部集合 → 临时 Collection（落 `uploaded_collections/`）→ 与手工执行共用 `run-postman` 队列与 worker，执行器零改动；`report_name` 形如 `project_<pid>_<时间>_<job前8位>.html`，嵌 job_id 保证重启后不撞名且可逐字节命中报告。
- 懒对账（A3 详情打开时触发）真值优先级：**磁盘报告 > 内存任务 > unknown**；通过/失败数读自报告 summary；历史「入队即记录」，不会永远挂起。
- CAS 乐观锁：A4 项目更新、A11 追溯整表必须回传 `updated_at`；409 时错误体 `data.current` 携带最新对象供前端合并。

### 17.3 数据与导出契约

- 项目目录 = `project.json` + 模板声明文件（`collections/*.json`、`tracing.json`、`docs/README.md` 等），集合/追溯均以相对路径登记，删除项目即整目录移除。
- 追溯行字段：`case_no` / `title` / `priority` / `convert_status`（`pending` 待转换 | `automated` 已自动化 | `manual` 手工）/ `collection_id` / `request_id`；服务端派生 `dangling`（关联集合已删）与总数/已自动化数/自动化率。
- CSV 固定 7 列：`case_no,title,priority,convert_status,collection_id,request_id,dangling`（dangling 转 0/1），UTF-8 BOM。
- zip 落共享导出目录（`uploaded_collections/exports`），arcname 全为项目目录相对路径（零逃逸）；下载复用 `/exports/<file_name>` 静态路由。

### 17.4 API 一览（15 个）

| # | 方法与路径 | 说明 |
|---|-----------|------|
| A1 | `GET /api/projects` | 列表（page/page_size/status/search） |
| A2 | `POST /api/projects` | 按模板创建 |
| A3 | `GET /api/projects/<id>` | 详情（含统计与执行历史，触发懒对账） |
| A4 | `PUT /api/projects/<id>` | 更新（name/description/status/metadata/config，带 updated_at CAS） |
| A5 | `DELETE /api/projects/<id>` | 删除（body `{"confirm": true}`） |
| A6 | `GET /api/projects/<id>/collections` | 集合列表 |
| A7 | `POST /api/projects/<id>/collections` | 挂集合（body = Collection JSON） |
| A8 | `DELETE /api/projects/<id>/collections/<col_id>` | 移除集合 |
| A9 | `POST /api/projects/<id>/execute` | 一键执行 → `{job_id, report_name, status}` |
| A10 | `GET /api/projects/<id>/tracing` | 追溯表（rows/total/automated/rate） |
| A11 | `PUT /api/projects/<id>/tracing` | 追溯表整表替换（带 CAS） |
| A12 | `GET /api/projects/<id>/export/tracing.csv` | CSV 导出（文件流） |
| A13 | `GET /api/projects/<id>/export` | zip 导出 → `{file_name, url}` |
| A14 | `GET /api/project-templates` | 模板列表（内置+用户合并） |
| A15 | `POST /api/project-templates` | 上传用户模板（服务端重写 id，用返回值） |

执行状态轮询复用既有 `GET /api/run-postman-status/<job_id>`。
