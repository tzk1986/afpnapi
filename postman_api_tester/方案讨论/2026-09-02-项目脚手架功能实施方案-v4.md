## 二、v4 新增缺漏与修正（G-30 ~ G-39）

### G-30【P0】v3 执行统计回写方案有硬伤：依赖页面存活 + 任务状态非持久

- **v3 方案**（5.3 节）：前端轮询 `/api/run-postman-status/<job_id>` 完成后，调 record 接口幂等回写 history。
- **本轮代码证据**：
  1. `handlers/job_routes.py:411-416` `api_run_postman_status` 读 `get_run_job()`；`report_job_store.py:16/45` 为**内存结构**，容量 `RUN_JOBS_MAX=200`（report_server.py:357 configure_run_jobs）——**服务重启即全部丢失**，进行中任务永远停在未知态；
  2. 用户点执行后**关闭页面**（常态），回写不发生，statistics.last_execution/execution_history 永久缺条。
- **v4 定稿（替代 v3 5.3 回写段）**：**入队即记录 + 查询时懒对账**，纯服务端闭环：
  ```
  A9 execute 入队成功
   └─ 同步写 execution_history 头条：
      {job_id, report_name(提交时即生成并透传 build_run_postman_job_params:29),
       time, status:"queued", passed:null, failed:null}
  A3 GET /api/projects/<id>（或 executions 子查询）
   └─ 对 history 中 status ∈ {queued, running} 的条目懒对账（按 job_id 去重幂等）：
      a) report_job_store.get_run_job(job_id) 命中 → 回填 status/进度；
      b) 内存 miss（重启/淘汰）→ report_repository.find_report(report_name)：
         报告存在 → 以报告派生 passed/failed，status:"done"；
      c) 两者皆 miss → status:"unknown"（展示"状态已失效，可跳转报告中心确认"）。
  ```
  - **真值优先级：报告（磁盘）> 任务内存 > unknown**；
  - 前端不再需要专门的 record 端点：A9 响应后直接轮询既有 run-postman-status 展示**实时进度**，历史面板数据全部来自 A3 懒对账；
  - 仍零修改 `report_job_execution_service.py`/`report_job_store.py`（只 import 读），维持 R1"仅 2 个共享文件纯追加"。
- **理由**：统计是项目的长期资产，回写链路不能建立在"浏览器恰好开着"与"进程恰好没重启"两个脆弱假设上；报告才是持久真值源。
- **影响风险**：GET 详情的懒对账把写操作放进读路径（read-your-writes 变体），store 锁内执行，容量 cap=20 下开销可忽略；单测须覆盖"重启后报告存在→done 回填"用例。

### G-31【P1】创建表单字段硬编码 → 改为模板变量 schema 驱动

- **草案/v3 遗留**：草案 6.3 "所属系统"下拉硬编码（数字餐厅/基础平台/采购/ESP/浙大营养），模块/负责人为自由文本；v3 G-16 只补了必填校验，未解决**选项来源**——新增系统需改前端代码，且各模板必填集可能不同。
- **外部佐证**：cookiecutter choice/boolean 类型化变量、copier questions schema。
- **v4 设计**：template.json 新增 `variables` 数组：
  ```jsonc
  { "key": "system", "label": "所属系统", "type": "enum", "required": true,
    "options": ["数字餐厅", "基础平台", "采购", "ESP", "浙大营养"] }
  ```
  创建页按所选模板动态渲染表单；A2 后端按 schema 校验（缺必填→PRJ_202，enum 越界→PRJ_202）；`_unresolved` 机制（v3 G-20）保留作为最终兜底。内置 3 模板各自提供 variables 定义。
- **理由**：脚手架的"规范强制"目标（1.2 之 2）恰靠 schema 落地——枚举/必填只定义一次（模板），前后端同源；硬编码下拉会让三套内置模板的规范差异退化成前端 if-else。
- **影响风险**：无既有代码涉及；A2/A14 响应体增加 variables 字段（新增接口，无兼容负担）。

### G-32【P1】模板渲染改为 files manifest 声明式（吸收 plop actions 思想，修正 v3 G-20 的实现面）

- **v3 遗留**：create_project 仍**硬编码**生成 `docs/README.md`、`docs/troubleshooting.md`、示例 collection 与 tracing.json——模板想多/少一个文档文件需要改 Python。
- **v4 设计**：template.json 用统一 `files` 清单声明生成物：
  ```jsonc
  { "path": "docs/README.md",           // 相对项目根，过 sanitize_export_name 级路径校验（禁 ../、绝对路径）
    "content_template": "# {{project_name}} …",
    "render": true }
  { "path": "tracing.json", "content_template": "{...json 字符串...}", "render": false }
  ```
  service 通用循环：路径校验 → 受限占位符替换（render=true 才替换，对应 cookiecutter "copy without render"）→ atomic 写盘；`collections/` 示例集合亦由 files 项声明（含 x_assertions 示例）。**禁止** script/hook/pre/post 字段（外部反例，见第一节）。
- **理由**：声明式清单是本次调研四个外部工具的最大公约数；v3 的"受限键替换"规则不变，只是从"散落在 service 里的 3 处手工生成"收敛为"1 处通用引擎"，测试面也更小。
- **影响风险**：files.path 是新的用户可控路径输入面（用户模板 POST A15 可自定义模板）——每个 path 必须 `resolve().is_relative_to(project_dir)` 断言，此项并入 v3 冲突 3 的四重防护体系统一实现（G-33 合并测试）。

### G-33【P2】用户模板创建接口（A15）的输入面需要独立定稿

- **v3 遗留**：A15 只有一行"创建用户模板（写 user 目录）"，未定义：模板 id 生成、名称唯一性（同名内置拒绝 TPL_002）、files.path 校验（v3 冲突 3 防护需扩展至模板声明期——**在 A15 时即校验 path 合法性，而非等到创建项目时**，fail fast）、大小上限（模板 JSON ≤ 256KB，常量 `PROJECT_TEMPLATE_MAX_BYTES`，对齐 GLOBAL_VARIABLES_MAX_COUNT 式配额惯例 config.py:473）。
- **v4 定稿**：A15 请求体 = 完整 template.json（服务端重写 `id`/`author`/`created_at`，拒绝客户端 id）；声明期校验：schema 合法 JSON、path 白名单正则、variables.key 唯一、content_template 长度上限；用户模板目录写入走 atomic_write_json。
- **理由**：A15 是脚手架**唯一的任意内容落盘入口**，声明期校验能把 G-20/G-32 的所有路径风险前移到单点。

### G-34【P2】`request.get_json()` 必须 `silent=True`——草案写法会绕过统一响应契约

- **草案位置**：5.3.1 `data = request.get_json()`。
- **现有代码事实**：全仓约定 `request.get_json(silent=True) or {}`（collection_routes.py:88/134、global_variables_routes.py:155/232、job_routes.py:338）；不带 silent 时非法 JSON 触发 Flask 默认 400 **HTML** 错误页，与 L-1 包装体割裂，前端回退链拿到整页 HTML。
- **v4 要求**：project_routes 全部 POST/PUT 统一 `silent=True` 后显式 400（PRJ_101 段）；并入代码 review checklist。
- **理由**：新文件出生即遵守 L-1 的"最后一米"正是错误响应体本身。

### G-35【P2】数据模型 v3 增量：`template_info` 字段（配合 G-30 之外的演进留门）

- **v3 5.1 模型追加**（顶层）：
  ```jsonc
  "template_info": { "id": "tpl_api_basic", "version": "1.0.0",
                     "source": "builtin", "answers": { "system": "数字餐厅", … } }
  ```
- 用途：克隆项目（9.1 短期扩展）直接复用 answers 预填表单；未来若评估"模板升级"（copier update 模式）已有比对基线。**首版只写不读**（除克隆展示），零额外逻辑。
- **理由**：留痕字段成本≈0，缺它则克隆功能要重新发明答案采集；这是 copier answers 设计的最小成本移植。

### G-36【P2】PUT 项目（A4）补乐观锁，与 A11 对齐

- **v3 遗留**：A11 tracing 整表替换带 updated_at CAS（乐观锁），A4 项目更新未提——两人都开编辑页时 last-write-wins 静默覆盖。
- **v4 定稿**：A4 请求体必须回传 `updated_at`，不匹配→409 PRJ_305；冲突时响应携带最新对象供前端合并提示。白名单更新字段列表：name/description/status/metadata/config。
- **理由**：多管理员内网场景，静默覆盖属数据完整性缺陷；机制与 A11 同构，实现与测试可共用一套 CAS 工具函数。

### G-37【P2】导出 zip 落共享 EXPORTS_DIR 的命名与生命周期

- **代码事实**：`/exports/<path:filename>`（report_server.py:397）由 `serve_export` 提供（server_routes.py:183-185，`send_from_directory(EXPORTS_DIR, as_attachment=True)`）；EXPORTS_DIR = `uploaded_collections/exports`（:49）——与 Collection 导出文件**混住**。
- **v4 定稿**：文件名 `proj_<id>_<UTC紧凑时间戳>_project.zip`（先过 sanitize_export_name）；生命周期与既有导出文件完全一致（不新增清理逻辑，行为对齐 M-11 结论——由既有 cron 管辖）；文档注明"导出文件保留在共享导出区，与报告上传中间件同级"。
- **理由**：v3 A13"复用 /exports/"结论正确但缺命名规范，共享目录混住时前缀可区分来源，避免排查期误认。

### G-38【P2】路由/endpoint 命名唯一性与参数转换器

- **核实**：现有路由无 `projects` 前缀占用（report_server.py grep 零匹配）→ `/projects*` 页面与 `/api/projects*`、`/api/project-templates` 安全。
- **要求**：① report_server.py 中函数/endpoint 名用 `projects_*`/`api_projects_*` 前缀，避免与既有 38 条及 handlers import 别名撞名；② `<project_id>`/`<col_id>` 用默认 **string 转换器**（拒绝 `/`），**不要** `<path:...>`——与既有 `<path:report_name>` 不同，我们的 id 是封闭格式，path 转换器只会扩大攻击面（对照 v3 冲突 3）；run-postman-status 的 `<path:job_id>` 属既有行为，不动；③ 新页面遵循现有壳页模式（如 `/ui-testing` 纯 render），不引入 SPA fallback 依赖。
- **理由**：path 转换器对固定格式 id 是纯粹的攻击面增加；endpoint 撞名在 create() 时才暴露，浪费排障时间。

### G-39【P2】文档治理：草案悬空引用

- **发现**：v1.0 头部"关联文档：《自动化测试方案调研对比分析报告.md》附录 G（Seldom 调研）"——**该文件不存在**（方案讨论目录仅有 `2026-06-12-同类项目调研对比与功能演进方案.md`）。
- **v4 处理**：实施时最终交付文档（README/操作手册/知识库）的引用一律指向真实存在的文件；v3 接口总表（5.2）中 A13 描述按 G-37 更新命名，5.3 回写段按 G-30 重写——**以 v4 为准**。

## 三、v4 设计增量汇总（合并进实施基线）

1. **数据模型**：project.json 顶层 + `template_info`（G-35）；`variables` schema 进 template.json（G-31）；`files` manifest 取代 doc/collection 硬编码生成（G-32）。
2. **接口总表变更（对 v3 5.2）**：A3 GET 详情响应含**懒对账后**的 history（G-30）；A9 响应 data 增 `report_name`（供进度页即时展示）；A15 请求/校验规则定稿（G-33）；**删除** v3 5.3 提到的 `POST /api/projects/<id>/executions/record`（被 G-30 取代，权威表变 3 页 + 15 API 不变）。
3. **执行记录状态机（新增，v3 无）**：`queued → running → done|failed`（内存对账）；`queued/running` 且内存 miss → 报告存在 `done`，否则 `unknown`（终态，不再对账）。history 条目不可删，cap=20 截尾保头部最新（G-23 不变）。
4. **校验前移原则（G-33）**：路径合法性在**声明期**（A15）与**使用期**（A2 创建实例化 files）双重校验——用户手写 projects/ 目录文件无法绕过运行时校验。
5. **测试矩阵增补（对 v3 5.5）**：
   - store：files.path 声明期非法（`../`、绝对路径、盘符、Windows 保留名）双重拒绝；
   - service：G-30 三条对账分支各 1 例（含"内存 miss + 报告存在→done"模拟重启场景，monkeypatch get_run_job→None）；schema 校验 enum 越界→PRJ_202；CAS 冲突→409；
   - routes：非法 JSON body→统一包装 400（G-34）；模板 >256KB 拒绝；
   - 人工：模板 variables 切换时表单动态重建；克隆页 answers 预填（若首版做只读展示）。
6. **配置常量增补**：`PROJECT_TEMPLATE_MAX_BYTES=262144`、`PROJECT_EXECUTION_HISTORY_MAX=20`（并入 v3 G-23/G-27 的 `_env_int` 惯例清单）。
7. **分期微调（对 v3 六节）**：阶段 1 增加"schema 渲染 + manifest 引擎"（约 +1 天）；阶段 3 的 record 端点工作项删除，改为懒对账单测；阶段 4 增加"内置 3 模板补 variables/files 字段"。

## 五、决策点（v4 终版）

| 决策 | v4 定稿建议 |
|------|------------|
