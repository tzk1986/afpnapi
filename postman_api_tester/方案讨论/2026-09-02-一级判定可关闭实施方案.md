# 一级判定可关闭实施方案（v1.37.17 提案）

- **日期**: 2026-09-02
- **前置版本**: v1.37.16（JSONPath 断言三步收口完成：21574a3 / ed627d5 / 1dcf1f9）
- **需求来源**: 用户实测——为接口配置断言 `$.errCode eq 100002` 后执行，响应为"session 已经过期"（HTTP 200，errCode=100001，message 不含成功关键词），**一级结果判定先判 FAILED，二级断言根本没跑**，报告详情看不到断言结果表，无法验证断言功能是否正常。用户要求：**一级判定（errCode/message）要能关闭，只用断言判定结果**，便于调试断言。
- **状态**: 已实施（v1.37.17，2026-09-02），见文末"七、实施偏差回写"。

## 一、现状走查（实证）

### 1.1 两级判定顺序（既有设计，v1.37.14 维持）

`executor.py` :462-496：

```
_evaluate_judgment(errCode/message/expected_status)
  ├─ 通过 → _run_assertions → 断言失败翻 FAILED（:250-258）
  └─ 失败 → _build_judgment_failed_result，断言不执行、结果无 assertion_results 字段
```

用户报告（`reports/Collection_20260902_191105_meta.json`）正是走了失败分支：message="判定失败: message 缺少成功关键词(期望为 ['success'])…"，结果条目 keys 无 `assertion_results`。**链路本身无 bug，属设计顺序**（方案一验收矩阵 F-7 固化的语义）。

### 1.2 判定开关体系——引擎层早已支持，缺的是入口

四层优先级解析在 `utils/judgment_utils.py::resolve_judgment_params`（:80-132）：**任务级 > 集合接口级 x_* > 全局 config > 内置默认**。各层现状：

| 层 | 开关 | 现状 |
|---|---|---|
| 全局 | `ENABLE_ERR_CODE_JUDGMENT` / `ENABLE_MESSAGE_JUDGMENT`（config.py / report_server_config.py） | ✅ 已支持关闭，但需改配置文件 + 重启服务，体验重 |
| 集合接口级 | `x_enable_err_code_judgment` / `x_enable_message_judgment`（bool，随 Collection JSON） | ✅ parser bool 分支可透传，但**无编辑 UI**，只能手工编辑 JSON |
| 任务级 | `judgment_config.enable_err_code_judgment` / `enable_message_judgment`（bool） | ⚠️ **executor 已支持消费**（:718/:720 `_opt_bool(task_jcfg.get(...))`，False 生效覆盖），但 **handler 入口解析丢弃这两个键**——见 1.3 |
| 内置默认 | errCode 判定默认关、message 判定默认开 | — |

### 1.3 入口层缺口（本方案唯一要补的代码点）

`handlers/job_routes.py`：

- `_parse_judgment_config_from_form`（:117-129）：只解析 `judgment_success_err_codes` / `judgment_success_messages` 两个键，**"填写即启用"语义天然无法表达 False（关闭）**。
- `_parse_judgment_config_from_payload`（:132-144）：同样只透传 success 两键，`judgment_config` 里即使前端传了 `enable_*=false` 也会被过滤掉。

UI 侧对应：首页"判定条件配置"折叠区（index.html :301）只有两个 success 关键词输入框；编辑器执行弹窗无判定相关控件；ad-hoc 页 payload 通道同受 :139-142 过滤限制。

### 1.4 不受影响的链路（已核实）

- **HTTP 状态码判定**：`evaluate_result_judgment` :45 `status_code == expected_status` 无条件执行，**不在"一级判定"关闭范围内**（本方案语义=只关 errCode+message 两个业务维度，状态码兜底保留）。
- **登录/取 token 链**：executor 仅做 token 注入（:535-545），无内部登录判定；登录配置执行与 test_token 为独立链路，不消费任务级 `judgment_config`，关闭开关不误伤登录。
- **`ENABLE_ASSERTION_STRICT_MODE`**：只管断言引擎异常分支，与此正交。
- **约束 3.10.5**：`/api/run-postman` 表单新增字段向后兼容（不传=现状行为），非稳定接口契约变更。

## 二、方案设计（推荐 A）

### 方案 A：任务级"关闭一级判定"开关（推荐，最小闭环）

**语义**：单次执行范围内，勾选后本轮所有接口的 errCode 判定与 message 判定同时关闭，成败由「HTTP 状态码 + JSONPath 断言」决定。仅调试用，不影响集合持久配置。

改动面（4 文件）：

1. **`handlers/job_routes.py`**（~12 行）
   - `_parse_judgment_config_from_form`：新增解析 `judgment_disable_first_level`（值为 `"1"` 时）→ `config["enable_err_code_judgment"] = False; config["enable_message_judgment"] = False`。不传=完全现状（None 透传语义不变）。
   - `_parse_judgment_config_from_payload`：`judgment_config` 中 `enable_err_code_judgment` / `enable_message_judgment` 若为 bool 类型则透传（`isinstance(v, bool)` 精确判断，避免字符串脏值）。组合键 `disable_first_level: true` 同样展开为两 False（给 ad-hoc/脚本通道一个省事写法）。
2. **`templates/collection_editor.html` 执行配置弹窗**：新增 checkbox
   `☐ 关闭一级判定（errCode/message），仅按断言判定成败（调试用）`
   勾选 → `formData.append('judgment_disable_first_level', '1')`。勾选且当前无任何接口配置断言时给一次 confirm 提示（否则结果几乎恒 PASSED，属预期但易误解）。
3. **`templates/index.html`「判定条件配置」折叠区**：同款 checkbox（同一表单字段名，首页执行链路零额外后端改动）。
4. **`tests/`**：见 §四测试项。

引擎/工具层（executor.py、judgment_utils.py、report_job_execution_service.py、execution_helpers.py、postman_api_tester.py）**零改动**——消费链已通，只是入口没接线。

### 行为语义表

| 一级判定 | 配置断言 | 实际判定依据 | 场景 |
|---|---|---|---|
| 开（默认/不传） | 有 | 判定→断言 两级（现状） | 正常回归 |
| 开 | 无 | 仅判定（现状） | 正常回归 |
| **关** | **有** | **状态码 + 断言（断言必执行）** | **目标调试场景**：session 过期响应下，详情弹窗可见断言结果表 ❌ expected=100002 / actual=100001，message="断言失败: …" |
| 关 | 无 | 仅状态码（近乎恒 PASSED） | UI confirm 提示拦截误用 |

### 备选（不推荐首期）

- **B：编辑器逐接口 x_enable_\* 编辑区**——粒度更细（同一轮执行部分接口关、部分开），但需新增页签区块 + parser 白名单核对 + 往返测试，改动面大；等真实需求出现再作。
- **C：仅文档指引改全局配置**——零代码，但要改两个 config 文件并重启，且影响所有集合，调试体验差。

## 六、结论

引擎层四级开关体系早已支持关闭一级判定，真正的缺口只有 handler 入口解析"填写即启用"无法表达 False、UI 无控件三个点。方案 A 以 ~12 行后端解析 + 两处 checkbox 的最小改动接通全链，默认行为零变化，与自愈排期零交集。**待用户确认后按方案 A 实施。**

## 七、实施偏差回写（v1.37.17）

1. **编辑器 checkbox 落位工具栏而非"执行配置弹窗"**：方案 §二.2 假设编辑器有执行前配置弹窗，实际 `collection_editor.html` 无此弹窗（"执行"按钮直接走 save→run 链），故控件放在工具栏导出与执行按钮之间（`#disableFirstLevelJudgment`），`executeCollection()` 开头读取；勾选且 `collectionHasAnyAssertions()` 为 false 时 confirm 拦截（W-3 语义不变）。
2. **confirm 提示仅编辑器侧做**：首页提交时 Collection 尚未解析（只有上传文件句柄），前端无法预知是否含断言，文案降级为 label 内嵌提示"若集合无断言，结果近乎恒 PASSED"。
3. 其余（job_routes 两解析函数、index.html checkbox、W-5/W-6 测试 `tests/test_judgment_disable.py` 14 项、门禁 2385 全绿 + mypy 零错、6 文档 v1.37.17）与方案一致。
4. **与 v1.37.18（接口级）关系**：本版=任务级临时调试开关；v1.37.18=接口级持久配置 + 集合级共享断言（见 `2026-09-02-接口级一级判定关闭实施方案.md`），引擎优先级任务>接口>全局天然分层，零协调代码。
