# 自定义一级判定规则实施方案（v1.37.21 提案）

- **日期**: 2026-09-02
- **需求来源**: 用户在 v1.37.17 收尾、v1.37.18（接口级开关+共享断言）开工前提出——"一级判定是否可以做成**自定义形式**，**增加一级判定**，或者**整体关闭不使用**"。
- **诉求拆解**（三件事，可行性各不相同）：
  1. **增加自定义判定**：一级判定现仅内置三维度（状态码/errCode 白名单/message 关键词），用户想按**任意响应字段**定义成败标准（如 `$.data.status eq ok`、`$.code ne 500`），且属于"判定"层语义（失败短路断言、message 前缀"判定失败"）。→ **可做**，复用断言引擎求值、挂进判定阶段。
  2. **整体关闭不使用**：判定层完全不参与成败（含本版自定义规则）。→ **大部分已有**：v1.37.17 任务级 checkbox、v1.37.18 接口级三态、全局 config 双 False；本版把"关闭"语义**扩展到自定义规则**（关闭=errCode+message+自定义规则全关）。**HTTP 状态码兜底不可关**（设计红线，见 §2.4）。
  3. **与 v1.37.18 共享断言的关系**：见 §四正交性分析——自定义判定=判定层的用户扩展；共享断言=断言层的集合复用。两者不同层，不互相替代。
- **状态**: 方案讨论，待用户确认。实施前不动代码（v1.37.18 先行）。

## 一、现状走查（实证）

### 1.1 判定层结构（扩展点在哪）

```
executor.execute_test
  ├─ _process_response → response_data / err_code / message   (:442-449)
  ├─ _evaluate_judgment(api, status_code, err_code, message)  (:463)
  │     └─ resolve_judgment_params 四层优先级 (judgment_utils.py:80-132)
  │     └─ evaluate_result_judgment (:25-43)：
  │           status_code == expected_status（无条件，红线兜底）
  │           + enable_err_code → errCode ∈ success_err_codes
  │           + enable_message  → message 含 success_messages 任一关键词
  ├─ 判定失败 → _build_judgment_failed_result，断言不执行      (:484-496)
  └─ 判定通过 → _run_assertions → 断言失败翻 FAILED            (:467-483)
```

**关键观察**：`_evaluate_judgment` 现签名只拿 `err_code`/`response_message` 两个抽取后的标量，**拿不到完整响应体**（`response_data` 在 :444 已解出、:449 存 `self.response_data`）——自定义 JSONPath 判定必须把 `response_data` 传入，这是本方案唯一的引擎触点。

### 1.2 可复用件（零新造轮子）

| 件 | 位置 | 复用方式 |
|---|---|---|
| 规则结构+归一化防腐 | `assertions.normalize_assertion_rules`（三入口共用） | 自定义判定规则用**同一 `{path,op,expected}` 三元组**与同一归一化 |
| 求值引擎 | `_evaluate_assertions(response_data, rules)`（executor 模块级导入） | 判定阶段直接调用，逐条 `passed` 聚合 |
| 解析链 | `parser._parse_x_extensions` list 分支（:278-283） | 新模式加一个 list 字段即可 |
| 编辑器往返 | `collection_editor_service` parse/build + normalize（v1.37.15 模式） | 同 x_assertions 处理方式 |
| UI 行组件 | 断言页签断言行（path/op 13 下拉/expected） | 复用渲染 |

### 1.3 "关闭"语义现状（需求 2 的既有拼图）

| 粒度 | 入口 | 版本 | 状态 |
|---|---|---|---|
| 全局 | `ENABLE_ERR_CODE_JUDGMENT` / `ENABLE_MESSAGE_JUDGMENT` 置 False | 早已有 | ✅ 持久，需重启 |
| 任务级 | 「关闭一级判定」checkbox / payload `disable_first_level` | v1.37.17 | ✅ 已交付（本次提交） |
| 接口级 | `x_enable_*` 三态（编辑器 UI） | v1.37.18 | 🔧 实施中 |
| 状态码 | `x_expected_status` 可调期望值，但判定不可关 | — | 保留为红线（§2.4） |

## 二、方案设计

### 2.1 字段契约

| 字段 | 层 | 类型 | 语义 |
|---|---|---|---|
| `request.x_judgment_rules` | 接口级 | list（同断言三元组，normalize） | 该接口自定义判定规则，**AND 语义**，任一失败→判定层 FAILED（短路断言） |
| `x_shared_judgment_rules`（P1，可停车场） | 集合级 | list | 注入全部接口判定层，与 item 自有合并（shared 在前），item `x_skip_shared_assertions` 同步豁免（复用同一豁免开关，语义=本接口不受集合共享约束） |

不引入新操作符、新表达式语言——**就是断言三元组换在判定阶段执行**。

### 2.2 执行链改动（唯一引擎触点）

- `parser._parse_x_extensions`：新增 list 分支 `x_judgment_rules`（normalize，source="parser"）；`ApiConfig` 补声明。
- `executor._evaluate_judgment` 签名补 `response_data: object`；在 `evaluate_result_judgment` 通过后**追加**自定义规则评估：
  ```
  内置维度通过 → 取 rules = shared? + api.get("x_judgment_rules")
                → _evaluate_assertions(response_data, rules)
                → 任一失败：passed=False，fail_reason 追加 "自定义判定失败: msg1; msg2"
  ```
  内置维度已失败时**不再评估自定义规则**（保持短路顺序，fail_reason 不混排）。
- **关闭语义联动（需求 2）**：任务级 `judgment_disable_first_level` / 全局 config / 接口级 `x_enable_*=false` 的既有开关**同时关闭自定义规则**——实现上：自定义规则评估放在 `_evaluate_judgment` 内、受一个 `first_level_effectively_off` 局部判断控制（errCode 与 message 两维度均为 False 时视为主判定关闭态，跳过自定义规则）。**理由**：用户关一级判定的心智=判定层不接管成败，自定义规则是判定层的一部分，不能关了开关还残留。
- jsonpath-ng 未安装：自定义规则视为不通过并给提示（与断言引擎现状一致，`_ASSERTIONS_AVAILABLE` 已在 executor 消费）。

### 2.3 编辑器

- §2.2（v1.37.18）"一级判定"小节下追加「自定义判定规则」列表区（复用断言行组件 + 增删按钮），写 `state.editBuffer.x_judgment_rules`；说明行："判定阶段执行，任一失败直接判 FAILED 且**不再执行断言**；成功标准类规则建议放断言（判定关闭时仍执行）"。
- service 往返：v1.37.18 的 5 字段基础上 +`x_judgment_rules`（normalize，空不写）；根级 `x_shared_judgment_rules`（P1）。
- 报告零改动：失败聚合进 `message`，详情弹窗已有判定失败展示。

### 2.4 设计红线（明确不做）

- **状态码判定不可整体关闭**："整体关闭不使用"= 关闭 errCode/message/自定义规则，`expected_status` 兜底保留——关掉它则连接层失败（5xx/超时前 HTTP 层异常已有 ERROR 兜底，但 4xx/5xx 响应体合法的将恒 PASSED），回归结论失真。真有"只信断言"的场景，配 `x_expected_status` + 断言即可覆盖。
- **不做 or 语义 / 条件嵌套**：判定规则维持 AND，复杂逻辑归断言层或拆用例。
- **任务级不传自定义规则**（judgment_config 不扩 rules 键）：任务级已有"一键全关"（v1.37.17），临时增加判定规则的需求由 ad-hoc/编辑器承载，YAGNI。

## 三、行为语义矩阵（集成后全景）

| errCode/message 开关 | 自定义规则 | 断言（自有+共享） | 实际判定 |
|---|---|---|---|
| 开 | 无 | 有 | 内置→自定义(空)→断言 两级（=现状） |
| 开 | 有 | 有 | 内置 ∧ 自定义 通过→断言；任一判定失败短路 |
| **关** | （被联动关闭） | 有 | 仅状态码 + 断言（v1.37.17/18 语义） |
| 开 | 有 | 无 | 内置 ∧ 自定义 |
| 关 | （关闭） | 无 | 仅状态码（近乎恒 PASSED，既有提示） |

## 四、与 v1.37.18 的关系与交付顺序

- **正交**：v1.37.18 管"开关与断言的集合复用"，本版管"判定层的规则扩展"。文件改动面交叠于 `collection_editor.html` 同一小节、`collection_editor_service` 同一函数、`parser` 同一函数——**同文件不同语义块，必须 1.37.18 先行合并后 rebase 式续做**，避免双版同文件并发提交冲突。
- **交付**：v1.37.21 PATCH（原拟 v1.37.19/20 号位已分别由夜间走查修复与断言落盘修复占用），依赖 v1.37.18 已落地；P1（集合级共享判定）视需求热度可与本版拆分顺延。

## 五、风险与对策

| # | 风险 | 等级 | 对策 |
|---|---|---|---|
| K-1 | 用户混淆"自定义判定规则"与"断言"（两者结构相同、阶段不同） | P2 | UI 说明行点破核心差异：**判定失败短路断言、断言失败不短路**；关闭一级判定时自定义规则一并失效；操作手册对照表 |
| K-2 | 判定层调用 `_evaluate_assertions` 抛引擎异常（现状判定层无 try 保护） | P3 | 包 try：异常时 fail-open？否——**fail-closed 记判定失败并透传异常信息**（与 strict 模式语义对齐），不吞错 |
| K-3 | 关闭联动后用户发现"关了开关自定义规则也没跑"困惑 | P3 | 正是设计意图（§2.2），报告 message 与 UI 文案写明"一级判定已关闭（含自定义规则）" |
| K-4 | response_data 非 dict/JSON（HTML 响应） | P3 | JSONPath 求值对非 JSON 返回失败 → 判定失败提示，符合预期；不加特判 |
| K-5 | 与自愈 v1.38.0 冲突 | 无 | 改动面 executor/parser/editor——与自愈白名单零交集 |

## 九、结论

"增加一级判定"可行且便宜：规则结构、归一化、求值引擎全部复用断言设施，引擎触点只有 `_evaluate_judgment` 一处（补传 `response_data` + 判定通过段追加规则评估）。"整体关闭"已由 v1.37.17/18 三层开关覆盖，本版把关闭语义**联动到自定义规则**，唯状态码兜底保留为红线。与 v1.37.18 正交但同文件，**必须待 v1.37.18 落地合入后再实施本方案**。**待用户确认。**
