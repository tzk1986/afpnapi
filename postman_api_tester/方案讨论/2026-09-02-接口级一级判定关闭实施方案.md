# 接口级关闭一级判定 + 集合级共享断言实施方案（v1.37.18 提案）

- **日期**: 2026-09-02（同日二轮扩充：融合"共享断言统一判断"形态）
- **需求来源**: 用户在 v1.37.17（任务级关闭开关，方案 A）实施中途提出——"是否可以**针对某一个接口**关闭一级判定，以便**统一管理所有的接口用例（包含失败判断断言用例）**"；二轮追加——"errCode/message 也可以用断言来判断，在断言中**勾选统一判断**，只要一个断言勾选了，就在所有接口中判断；不勾选就是单独判该接口"。
- **典型场景**: 同一 Collection 混合正常用例与异常用例。异常用例（如参数校验失败）业务返回 `errCode=100002`，对该用例而言这是**预期成功**，由断言 `$.errCode eq 100002` 判定；但只要一级 message/errCode 判定开着，它必被判 FAILED，整集合同一条链跑不通。需要**接口级**关闭一级判定、让断言接管成败，其余用例维持默认——集合即自描述、可统一回归管理。
- **融合形态结论**: 用户的"统一判断"诉求不靠给接口级断言加 checkbox 实现，而是**新增集合级共享断言**（写在共享区的规则自动作用于全部接口，等价"勾选统一判断"；不写进共享区就是接口单独判断）。同时**保留接口级关闭开关**作为异常用例的豁免机制——共享断言 `$.errCode eq 0` 对预期 100002 的异常用例必杀，没有接口级豁免，"统一管理"反而挤死异常用例。
- **状态**: 方案讨论，待用户确认。实施前不动代码。

## 一、现状走查（实证）

### 1.1 接口级引擎链路已完全就位（历史能力，2026-06-11 可配置判定方案交付）

| 环节 | 证据 | 状态 |
|---|---|---|
| Collection 字段契约 | `request.x_enable_err_code_judgment` / `x_enable_message_judgment`（bool） | 已定义 |
| parser 透传 | `parser.py:244-256` bool 白名单分支（含 `"true"/"1"/"yes"` 字符串归一化）；`ApiConfig` TypedDict 声明 :55-56 | ✅ |
| executor 消费 | `executor.py:714/716` 作为 item 层入 `resolve_judgment_params`，四层优先级 **任务级 > 接口级 > 全局 > 默认**（`judgment_utils.py:103-119`） | ✅ |
| ad-hoc 通道 | `collection_utils.py:484-502`（normalize）+ :636-641（build 写入）；用例级 `x_enable_*` 已可传 | ✅ |
| 接口测试代理 | `test_proxy_routes.py:92-94` 已消费 | ✅ |
| 变量替换跳过 | `variable_substitution.py:120-121` | ✅ |

**结论**：手工在 Collection JSON 里给某个 request 写 `"x_enable_message_judgment": false`，执行链今天就能正确关闭该接口的一级判定。

### 1.2 真实缺口（三个，缺一不可做）

**缺口 ①：编辑器无编辑入口。** 用户要"统一管理"，必须能在可视化编辑器里逐接口设置，而不是手改 JSON。

**缺口 ②（阻塞性 bug）：编辑器往返会静默丢弃 4 个判定字段。**
`collection_editor_service.py` 的 `_parse_request_node` 只提取 method/url/headers/params/body/x_extract/x_assertions/description；`_build_request_object` 只写回这些 + x_extract/x_assertions。因此：

```
手工在 Collection 写好 x_enable_*=false → 编辑器导入 → 点保存/执行（save→build）→ 字段丢失 → 一级判定复活
```

编辑器"执行"按钮内部先调 `/api/collection-editor/save` 重建 Collection（collection_editor.html executeCollection），所以**即使只做缺口 ②（补往返）不做 UI，对"纯手工 JSON 用户"也是必要修复**；只做 UI 不修往返则配置形同虚设。二者必须同版交付。

> 同类丢失还有 `x_repeat`、`x_pre_request`（编辑器往返同样不保留），与本需求无关，进停车场 §五，不搭车修。

**缺口 ③（二轮新增）：无"集合级统一判定"能力，逐接口配置管理成本高。** 用户二轮提出用断言承担 errCode/message 判定并"勾选统一判断"。走查实证该思路**部分可行但有边界**：

| 评估点 | 实证 | 结论 |
|---|---|---|
| errCode/message 断言化表达 | 13 操作符含 `eq`/`contains`，`$.errCode eq 0`、`$.message contains success` 均可写 | ✅ 引擎零改动 |
| 集合级注入先例 | ad-hoc 顶层 `assertions_json` 已注入每条用例（job_routes.py:399-404） | ✅ 机制相通 |
| 能否**替代**一级判定 | 判定失败短路断言不执行（executor.py:462-496）→ 替代的前提仍是一级判定关闭，绕不开缺口 ①/②；且 `SUCCESS_MESSAGES`/`SUCCESS_ERR_CODES` 是**任一匹配即通过（or 语义）**，断言规则间是 **and 语义**、单 op 单值，多关键词容错表达不了 | ⚠ 只能作为"关判定后的统一接管"，不能整体替代 |
| 异常用例豁免 | 共享 `$.errCode eq 0` 对预期 100002 用例必杀，需接口级关闭/自有断言豁免 | ⚠ 依赖缺口 ① 的接口级三态 |

故融合形态定为：**新增集合级共享断言（= "统一判断"）+ 保留接口级开关（= 豁免机制）**，两者配合才成立；"给接口断言加 checkbox 提升到全集合"的交互不做——共享区本身即"统一"语义，且避免"提升"后来源模糊（该规则到底属于接口还是集合）与二次提升叠加问题。

## 二、方案设计

### 2.1 service 层四字段往返（修缺口 ②）

`services/collection_editor_service.py`：

- `_parse_request_node` 补提取 5 字段进 flat：
  - `x_enable_err_code_judgment` / `x_enable_message_judgment` / `x_skip_shared_assertions`：与 parser 同口径归一化为 `Optional[bool]`（缺失=None，字符串 "true"/"1"/"yes"… → True/False）；
  - `x_success_err_codes` / `x_success_messages`：原样 str（编辑器不编辑、仅保留）。
- `_build_request_object` 补写回：bool 三字段 `is not None` 才写；success 两字段非空 str 才写。
- 防御：build 前对 bool 三值做 `isinstance(bool)` 校验（前端脏值丢弃 + warning，与 normalize_assertion_rules 防腐思路一致）。

### 2.2 编辑器 UI（补缺口 ①）——「断言」页签新增"一级判定"小节

位置：v1.37.15 断言页签顶部、断言规则列表之前（语义分组：判定方式与断言同页签，随 `ENABLE_ASSERTIONS` 显隐）。

控件（每接口独立）：

```
一级判定（关闭后该接口成败仅由 状态码 + 断言 决定）
  errCode 判定:  [继承(默认) ▾]   → 继承 / 强制开启 / 强制关闭
  message 判定:  [继承(默认) ▾]   → 继承 / 强制开启 / 强制关闭
```

- 两维度独立三态 select，映射：继承=不写字段（None）；强制开启=true；强制关闭=false → 写入 `state.editBuffer.x_enable_err_code_judgment / x_enable_message_judgment`（syncToAllRequests 深拷贝回传，保存时经 service build 写进 Collection）。
- 同小节追加 checkbox「共享断言豁免」（写 `state.editBuffer.x_skip_shared_assertions`，勾选=true / 取消=None 不写字段，语义见 §2.4）。
- "只看断言"（用户核心诉求）= 两个都选"强制关闭"，UI 文案在说明行点破；不另造组合快捷项（YAGNI，两 select 成本相同）。
- 重绘状态保持：select 当前值从 editBuffer 渲染（遵循 render 保状态既有约定）。
- 全值转义沿用 escapeAttr；本控件无自由文本输入，XSS 面为零。

### 2.3 与任务级开关（v1.37.17 方案 A）的关系

引擎优先级已定死语义，**零协调代码**：

| 任务级（执行弹窗/首页 checkbox） | 接口级（本页签） | 实际效果 |
|---|---|---|
| 未勾选（inherit） | 未设置 | 全局 config 判定（现状） |
| 未勾选 | 已设置 | **接口级生效**——统一管理混合用例的形态 |
| 勾选（关闭） | 任意 | 任务级 override 全部接口（调试临时用） |

两版关系：v1.37.17=任务级临时调试开关（入口补线，实施中）；v1.37.18=接口级持久配置（本方案）。文件改动面交集仅 `collection_editor.html` 同文件不同区块，分版提交无冲突。

### 2.4 集合级共享断言（二轮新增，补缺口 ③）

**字段契约**：Collection **根级** `x_shared_assertions`（list，元素同 `{path, op, expected}` 三元组，经 `normalize_assertion_rules` 归一化）。放根级而非 info 块：info 是 Postman 元数据约定区，根级已有 `variable` 等自定义先例，parser 读取最直接。

**执行链注入（parse 挂键、run 时合并，不提前 merge）**：

- `parser.py::extract_apis`：解析根级 `x_shared_assertions`（归一化一次），**逐条挂到每个 ApiConfig 的独立键** `x_shared_assertions`；**不并入 item 的 `x_assertions`**——防止共享规则被误当作接口自有断言持久化（编辑器往返、导出都会逐 item 落盘，提前合并会造成共享重复注入的滚雪球）。`ApiConfig` TypedDict 补声明。
- `executor.py::_run_assertions`（:742）：消费时合并 `shared + own`（**共享在前、自有在后**，报告展示顺序=全局约束先）；老集合无该键时 `api.get` 返回 None，行为与现状逐字段一致（零回归）。
- `variable_substitution.py`：根级 `x_shared_assertions` 与 item 级 `x_assertions` 同列入跳过清单（:120-121 既有约定），expected 不做 `{{var}}` 替换，语义一致。
- **ad-hoc 通道零改动**：顶层 `assertions_json`（job_routes.py:399-404）本就是"每条用例应用"的等价能力，维持现状不重构（YAGNI）。
- 报告详情零改动：合并进 `assertion_results` 后自然展示。

**编辑器往返**（与 §2.1 同一版交付）：

- `parse_collection_to_flat`：返回值新增根键 `x_shared_assertions`（normalize 后的 list，缺省 `[]`）。
- `build_collection_json`：非空才写回根级；空列表不写字段（保持集合干净）。

**编辑器 UI**：断言页签**顶部**新增「集合共享断言（作用于全部接口）」小节，位于 §2.2 一级判定小节之后、接口自有断言列表之前；规则行组件复用现有断言行（path/op 13 项下拉/expected，escapeAttr 全值转义）。**状态存集合层独立字段**（如 `state.sharedAssertions`），**不进 per-request editBuffer、不参与 syncToAllRequests**——它是集合属性，与"当前选中接口"无关；随整集合提交。随 `ENABLE_ASSERTIONS` 门控显隐。

**共享与一级判定的关系（三轮追问确认，勿误解为"覆盖"）**：

- 现有顺序=一级判定先跑、失败即短路（executor.py:462-496），共享断言并入第二级执行——**一级判定开着时共享断言救不了异常用例**。共享不能"覆盖"一级判定开关，只能在判定关闭后**接管业务成败的判定职责**。
- 表达力边界：`SUCCESS_MESSAGES` / `SUCCESS_ERR_CODES` 是**任一匹配即通过（or 语义）**，断言规则间是 and 语义、单 op 单值——"message 含 success 或 ok 都算过"这类多关键词容错**断言写不出**，该场景仍须保留一级判定白名单；单一硬标准（`$.errCode eq 0`）可完全接管。

**接口级共享豁免 `x_skip_shared_assertions`（三轮新增）**：

需求：某接口不执行共享断言、只判自有断言（如集合统一 `$.errCode eq 0`，但某接口无 errCode 字段或标准不同）。

- 字段：request 级 `x_skip_shared_assertions`（bool，字符串白名单归一化与 `x_enable_*` 同口径，进 parser bool_fields）；
- 注入点：**parser 挂键时判断**，该 item 命中 true 则**不挂**共享键——executor 合并逻辑零改动，语义集中一处；
- 不可用"一级判定强制关闭"兼职豁免：强制关闭+共享接管（本小节推荐形态）与"关判定也豁免共享"互相矛盾，必须独立开关；
- 编辑器：§2.2"一级判定"小节追加 checkbox「共享断言豁免（本接口只执行自己的断言）」，仅当集合配有共享断言时有意义（常显，说明行提示）；
- 编辑器往返：§2.1 字段清单从 4 个扩为 **5 个**（+`x_skip_shared_assertions`，Optional[bool] 三态）。

**推荐管理形态（三件套配合）**：

```
集合共享断言:  $.errCode eq 0            ← "统一判断"，接管全集合业务成败
一级判定:      任务级/全局关闭（或共享区配套提示引导）← 不关则判定先短路，共享断言白配
异常用例:      接口级三态"强制关闭" + 自有断言 $.errCode eq 100002 ← 豁免，不被共享 eq 0 误杀
正常用例:      什么都不配                 ← 共享断言 + 状态码即全部判定依据
```

## 三、行为语义与示例

混合集合（管理目标形态）：

```json
// 用例1 正常路径：不写任何 x_enable_*，message 判定 + 断言照常两级
{ "name": "查询成功", "request": { ..., "x_assertions": [{"path":"$.errCode","op":"eq","expected":0}] } }

// 用例2 异常路径：关闭一级判定，errCode=100002 由断言判"成功"
{ "name": "参数缺失应返回100002", "request": { ...,
    "x_enable_err_code_judgment": false,
    "x_enable_message_judgment": false,
    "x_assertions": [{"path":"$.errCode","op":"eq","expected":100002}] } }
```

整集同一轮执行：用例1 走两级判定，用例2 仅状态码+断言——报告汇总一次看全，正/异常用例统一管理成立。

共享断言形态（统一接管版，用户二轮目标）：

```json
{
  "info": { "name": "订单接口回归" },
  "x_shared_assertions": [
    { "path": "$.errCode", "op": "eq", "expected": 0 }
  ],
  "item": [
    { "name": "查询成功", "request": { ...,
        "x_enable_err_code_judgment": false,
        "x_enable_message_judgment": false } },
    { "name": "参数缺失应返回100002", "request": { ...,
        "x_enable_err_code_judgment": false,
        "x_enable_message_judgment": false,
        "x_assertions": [ { "path": "$.errCode", "op": "eq", "expected": 100002 } ] } }
  ]
}
```

执行时用例1 实际规则=`[共享 eq 0]`；用例2=`[共享 eq 0, 自有 eq 100002]`？——**注意 and 语义会把用例2 判死**（errCode 不可能同时 0 和 100002）。因此共享接管形态下，**异常用例需要在自有断言里覆盖语义或接口级豁免共享**。本版裁决：**共享规则始终与自有断言 AND 合并，不做同名 path 覆盖**（引擎简单性优先）；异常用例的正确表达=该接口共享断言不适用时，走 §三前一种形态（接口级关闭判定 + 自有断言，**不配共享 eq 0**，或共享区改配状态码类通用规则）。换言之：**共享断言适合"全集合统一成功标准"（如都要求 $.data exists、统一 errCode eq 0 的纯正常集合）**；混合正/异常集合的推荐形态仍是§三第一种（逐接口三态豁免、不配 eq 类共享）。两种形态各管各的场景，UI 说明行点破，避免用户把 `eq 0` 共享进混合集合后困惑。

## 五、停车场（登记不搭车）

- `x_repeat`、`x_pre_request` 编辑器往返同类丢失——另案修复（同 §1.2 机制，成本相近）。
- 编辑器 UI 直接编辑 `x_success_err_codes` / `x_success_messages` 关键词覆盖（本方案仅做保留不丢失）。

## 八、结论

本版融合两件事：**接口级关闭一级判定**（执行引擎 2026-06-11 就已打通，要做的只是修编辑器四字段往返丢失这一阻塞性前提 + 断言页签两个三态下拉）与**集合级共享断言**（"统一判断"诉求的落位：根级 `x_shared_assertions`，parse 挂独立键、run 时与自有 AND 合并，编辑器共享区+集合级往返）。"断言全面替代一级判定"的原始设想经走查**不成立**——判定失败短路使替代的前提仍是关闭开关、or 语义白名单断言表达不了、且无接口级豁免则共享统一必杀异常用例；故接口级三态是共享形态的地基而非可被替代物。与 v1.37.17 任务级开关语义正交、天然分层（任务>接口>全局）。改动面：编辑器 service/模板 + parser/executor/变量替换小增量 + 测试。**待用户确认后实施（建议顺序：先收尾 v1.37.17 方案 A，再开工本版）。**
