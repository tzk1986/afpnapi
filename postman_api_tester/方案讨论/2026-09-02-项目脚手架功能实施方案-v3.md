## 三、v3 新增缺漏清单（G-13 ~ G-28）

### G-13【P0】前端渲染存储型 XSS

- **草案位置**：6.2 `renderProjects` —— `template.replace(/{name}/g, project.name)` 后 `$list.append(html)`。
- **问题**：项目名/描述经 API 存入后，在**每个浏览列表页的用户**浏览器中作为 HTML 注入执行。创建项目接口无内容过滤，`name = "<img src=x onerror=fetch(...callback...)>"` 即成存储型 XSS；叠加草案自带 CSRF 面（服务无任何鉴权，内网裸奔前提下 XSS 可调用全部 14 个接口含 DELETE）。
- **改进内容**：禁用字符串拼接 + innerHTML/append 渲染，改 `document.createElement` + `textContent`（与现有页面写法一致，参考 report_view.html 结果表渲染）；确需模板字符串时必须统一 `escapeHtml()` 工具。删除/执行等破坏性操作按钮增加二次确认弹层（现有页面已有 confirm 模式可沿用）。
- **改进理由**：草案前端示例是唯一直接引入注入漏洞的代码，且因项目数据"人人可创建、人人可见"，属存储型而非反射型，必须首版修复。
- **影响风险**：纯新增页面内部问题，修复不影响现有页面。

### G-14【P0】`callback_url` 自环示例与 SSRF 防护直接矛盾

- **草案位置**：5.2.3 示例 `"callback_url": "http://localhost:5000/api/projects/<project_id>/callback"`。
- **问题**：v2 冲突 5 的 SSRF 策略（拒绝 loopback）会**拒绝草案自己给出的示例**——草案意图是"执行完成回调本项目接口写统计"。若放行 loopback，则整个 127.0.0.1 内网端口探测面被打开，SSRF 防护形同虚设。此外草案接口清单根本没有 `POST /api/projects/<id>/callback` 这个端点（第 5 个未登记接口）。
- **改进内容**：**v3 定稿——删除 callback_url 请求参数与 callback 端点**。执行完成后的统计回写改为**进程内钩子**：worker 任务完成 → `report_job_execution_service` 既有回调点（job 状态置 success/failed 处）以 `report_name`/`job_id` 为键调用 `project_service.record_execution()`（若归属困难，退而求其次：项目详情页前端轮询 `/api/run-postman-status/<job_id>` 时顺带触发懒回写）。外部 webhook（飞书）从首版范围整体移除（原 v2 决策点 3 定稿为 B：延后，且届时按 v2 冲突 5 防护）。
- **改进理由**：草案的真实需求是"执行完更新项目统计"，这是**进程内数据流**，不该用 HTTP 自调实现（多一个未鉴权回调端点 + 序列化往返 + 竞态）；删掉后 SSRF 攻击面从"新增"变"零新增"。
- **影响风险**：与执行服务回调点挂钩需修改 `report_job_execution_service.py`（共享文件），改为"修改"而非"纯追加"——见第七节 R9；若评审不接受，则用懒回写方案（仅新增代码）。

### G-15【P1】错误码三套定义互相冲突

- **草案位置**：5.2.1 表（PRJ_001=名称为空）、10.1 附录（PRJ_001=项目不存在）、5.3.1 代码（PRJ_001~008 又一组含义，api_create 与 api_get 复用 PRJ_004/006）。
- **问题**：同一码在不同端点/章节表达不同语义，排障与前端回退链无法依赖。
- **改进内容**：v3 重排唯一错误码总表（见 5.4 节），规则：**一码一义、全仓唯一、按端点组分段**（PRJ_1xx 通用、PRJ_2xx 创建、PRJ_3xx 执行……TPL_1xx、TRC_1xx），与 `json_error` 文档注释"模块前缀_序号"（base_handler.py:208）一致。
- **改进理由**：v1.37.x 十个 handler 文件已按此规则登记错误码，脚手架必须进同一命名空间管理，否则优化清单 L 系列会再次记"错误码治理"。
- **影响风险**：无既有码冲突（PRJ_/TPL_/TRC_ 前缀未占用，已在 base_handler 注释前缀清单之外新增需补登记一行）。

### G-16【P1】`status` 字段缺失但被过滤；`search` 参数未定义

- **草案位置**：5.2.2 列表支持 `status=active` 过滤、6.2 前端有状态筛选下拉与 `search` 参数；但 4.1 数据模型**没有 status 字段**，`list_projects` 中 status 过滤是 `# TODO`；search 后端完全未接收。
- **改进内容**：project.json 顶层补 `"status": "active" | "completed" | "archived"`（默认 active，更新接口可改）；列表接口接收 `status`（非法值 400 PRJ_1xx）与 `search`（对 name/description 做大小写不敏感子串匹配，服务端过滤）；PUT 接口白名单字段更新，status 枚举校验。
- **改进理由**：模型-接口-前端三层脱节是草案最典型的"设计未闭环"，实施时必然临时拍脑袋补字段，破坏数据一致性。
- **影响风险**：仅新增文件字段；已创建项目缺 status 时读取端默认 "active"（前向兼容）。

### G-17【P1】创建流程无完整回滚，失败残留脏目录

- **草案位置**：5.3.2 `create_project` —— 先 `mkdir`，仅"模板不存在"一个分支 rmtree；此后 docs 写盘、collection 生成、tracing 创建、save_project 任一步抛异常都留下半初始化目录，`list_all_projects` 会扫到（get_project 读不到 json 返回 None 可跳过，但目录永久泄漏）。
- **改进内容**：整个创建流程包 `try/except`，任何失败在 `finally` 等价位执行**带路径守卫的 rmtree 回滚**（复用冲突 3 防护）；成功后才 `save_project`（project.json 最后写，天然作为"提交标记"——目录内无 project.json 即视为垃圾，list 时顺手清理）。
- **改进理由**：文件系统的"事务"只能靠提交标记模拟；这是低成本的正确姿势，也顺带解决手工拷入残缺目录的脏数据。
- **影响风险**：list 时清理垃圾目录属破坏性小动作，需开关保护（默认仅跳过不删除，v3.1 再评估是否清）——保守处理避免 G-13 之外的误删面。

### G-18【P1】project_id 生成可碰撞；格式与正则需统一

- **草案位置**：5.3.2 `proj_{时间}_{微秒前6位}` —— 并发创建同一微秒即撞，`mkdir(exist_ok=False)` 抛 FileExistsError 变 500。
- **改进内容**：改为 `proj_` + `uuid.uuid4().hex[:12]`（对齐 `ui_case_store.py:30` 惯例）；冲突 3 的白名单正则同步定为 `^proj_[a-z0-9]{12}$`；模板 id 定为 `^tpl_[a-z0-9_]{2,32}$`。创建捕获 FileExistsError 重试一次。
- **改进理由**：时间戳 id 在快速连续操作（脚本化建项目）下不唯一；uuid 短码已被现有 store 验证够用且天然匹配白名单。
- **影响风险**：无。

### G-19【P1】Collection 文件按名称生成：中文名 + 同名覆盖 + 未 sanitize

- **草案位置**：5.3.2 `col_file = f"collections/{col_template['name']}.json"` —— 两个示例集合同名即互相覆盖；名称含 `/`、`\`、`..`、Windows 保留名（CON/NUL）或非法字符直接异常/穿越；中文文件名在 zip 导出与 git 归档中有编码兼容成本。
- **现有代码事实**：`file_utils.py:17` `sanitize_export_name` 即为此类问题准备。
- **改进内容**：collection 文件名固定 `collections/col_<id12>.json`（id 服务端生成），人类可读名仅存于 project.json 的 collections 索引 `name` 字段；任何以名称作文件名的接口（添加 collection、导入）先过 `sanitize_export_name` + 长度上限。
- **改进理由**：文件名与用户输入解耦是路径安全（冲突 3）的另一半；"按名寻址文件"会让删除 collection（按 id）与文件系统不一致。
- **影响风险**：无既有数据迁移（全新目录）。

### G-20【P1】模板占位符 `{{system}}` 无渲染机制，未传字段会残留进项目数据

- **草案位置**：4.2 `metadata_template` 含 `"system": "{{system}}"`；5.3.2 直接 `{**template["metadata_template"], **metadata}` 浅合并——用户表单没填 `system` 时，项目里就存着字面量 `{{system}}`；doc_templates 内容里的 `{{project_name}}` 草案说"render"但未给实现。
- **现有代码事实**：仓内 `{{ }}` 是 Jinja2 语法（HTML 模板必须 `{% raw %}` 保护，记忆约束 feedback_jinja2_raw_and_form_field）；项目 JSON 不经过 Jinja2，不会执行渲染。
- **改进内容**：模板渲染定义为**简单键替换**（白名单 `{{key}}` → `str.replace`，未提供的键替换为空串并记录 `metadata._unresolved: [keys]`）；**禁止用 Jinja2 `Template(...).render`**（用户可控模板内容 → SSTI 风险，自定义模板功能 POST /project-templates 等于让用户注入模板源码）；创建接口对 system/module/owner 三个必填 metadata 字段做 400 校验（草案 5.2.1 错误码已列 PRJ_004/005 但未实现）。
- **改进理由**：自定义模板 + Jinja2 渲染 = 服务端模板注入，是本项目安全红线（与 SSRF/XSS 同级）；键替换语义清晰且无执行面。
- **影响风险**：无；约束记录：docstring 注明"模板语法为受限占位符，非 Jinja2"。

### G-21【P1】页面路由与详情渲染模式不统一；edit 页未注册

- **草案位置**：5.3.1 `project_detail_page` 服务端 `render_template("project_detail.html", project=project)`，而列表页纯前端 fetch；页面清单有 4 页但 `register_project_routes` 只注册 3 页（**project_edit.html 无路由**）；detail 页找不到项目时返回 `json_error`（HTML 页面吐 JSON 错误体）。
- **改进内容**：统一**壳页面 + 客户端 fetch** 模式（现有页面全部如此：`/ui-testing`、`/collection-editor` 只 render 空壳，数据走 API）；detail 路由只渲染壳，404/403 判断放 API 层；补 `GET /projects/edit/<project_id>` 或详情页内嵌编辑（v3 倾向后者，减一页——与 5.1 接口收敛同步，见 5.2 总表）。
- **改进理由**：混合渲染模式导致两套错误处理；壳页模式与现有 20+ 页面一致，前端心智统一。
- **影响风险**：页面数 4→3（index/create/detail 含内嵌编辑），草案周计划阶段 2 工作量相应减少。

### G-22【P1】tracing 载体重定义：xlsx 不能当 GET/PUT JSON 接口的主数据源

- **草案位置**：5.1 `GET/PUT /projects/<id>/tracing`，主数据却是 `tracing.xlsx` 二进制；PUT 语义（传什么？整表替换？行级？）未定义；4.1 中 tracing 统计字段（total_cases/automation_rate）与 xlsx 内容双源。
- **改进内容**：主数据改为 `tracing.json`（行数组：用例编号/标题/优先级/转换状态/collection_id/request_id），`atomic_write_json` 落盘；`GET tracing` 返回 JSON 行 + 服务端实时派生 total/automated/rate（**不存派生值**，消除双源不一致）；`PUT tracing` 定义为整表替换（带乐观锁 `updated_at` 校验，防并发覆盖）；`GET /export/tracing.csv` 输出文件流（stdlib csv）；xlsx 导出按 v2 冲突 12 延后决策。
- **改进理由**：JSON 行数据可测试、可 diff、可 git，派生统计必须单源计算——草案的"自动化率不准"风险（8. 风险表"定期同步校验"）根因就是双源存储，删掉冗余存储即消除。
- **影响风险**：G-5 依赖：collection 增删时同步标记 tracing 行 `dangling`（引用失效），GET 时派生提示，不做级联删除（用户数据保守处理）。

### G-23【P1】统计回写与 `execution_history` 无界增长

- **草案位置**：4.1 `statistics.execution_history: []`，执行完成回写无上限；`total_requests`/`pass_rate` 存在 project.json（又一双源）。
- **改进内容**：execution_history 仅存 **job 摘要**（job_id/report_name/时间/通过失败数），cap=20（常量 `PROJECT_EXECUTION_HISTORY_MAX`，L-3 惯例）超出截尾；通过率等统计从既有报告体系**按 report_name 现查**（`report_results_service`），项目 json 不冗余存 pass_rate 快照（last_execution 只存指针与时间）。历史 job 关联的报告被删除时显示"报告已删除"（引用 `report_lock_service` 现有语义）。
- **改进理由**：单源原则同 G-22；报告才是结果真值，项目层只存指针——避免"报告中心删了、项目统计还在"的经典不一致。
- **影响风险**：读报告接口属既有 3.10.5 稳定端点，**只读复用不改**。
