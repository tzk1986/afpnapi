## 一、结论摘要

v1.0 草案的**功能设计（项目层概念、数据模型、接口清单）整体可行**，但**工程实现细节与本项目现行约束存在 12 处冲突**，若照草案实施会引入：响应契约分裂、路径穿越删除数据、SSRF、前端技术栈不一致、路由装配违规等风险。v2 在**保留全部功能目标**的前提下逐条修正，并明确"零触碰现有代码"的模块隔离边界。

| 级别 | 数量 | 说明 |
|------|------|------|
| P0（必须修正，否则引入缺陷/违规） | 6 | 响应格式、路由装配、路径安全、原子写、SSRF、功能开关默认值 |
| P1（应当修正，工程一致性问题） | 4 | 前端技术栈、分页 clamp、版本与文档同步、mypy/测试门禁 |
| P2（建议优化） | 2 | service 拆分粒度、tracing 新依赖 |

## 二、逐条符合性分析与改进（附代码证据与改进理由）

### 冲突 1【P0】响应格式：`"code": "success"` 字符串 → 违反 L-1 统一约定

- **草案位置**：所有接口示例返回 `{"code": "success", "data": {...}}`；前端 `if (response.code === 'success')`。
- **现有代码事实**：`postman_api_tester/handlers/base_handler.py:140` 的 `BaseHandler.json_response(data, status_code=200, message="OK")` 返回 **tuple (Response, status)**，body 为 `{code: int, message, data, timestamp}`；错误统一走 `json_error(message, status_code, error_code)`（base_handler.py:203，错误码命名规则"模块前缀_序号"如 `CE_PARSE_001`）或 `BaseHandler.error_response(exc, status, error_code)`（base_handler.py:164）。v1.37.x 全仓 L-1 迭代已完成 9 个 handler 文件的包装统一。
- **违反约束**：开发阅读文档"L-1 响应格式统一"及前端入口解包约定（`const data = raw.data || raw`）。
- **改进内容**：14 个新接口全部使用 `BaseHandler.json_response(payload)` 返回成功；错误用 `json_error(msg, status, "PRJ_xxx")`。**code 一律为 HTTP 数字状态码**，草案中的 `PRJ_/TPL_/TRC_` 错误码放入 `error_code` 顶层字段（与 CE_/COL_/JOB_ 前缀惯例一致，草案错误码命名本身合规，仅承载位置需调整）。
- **改进理由**：新接口若发明第三种响应契约（字符串 code），前端将同时存在 `code===200`、`code==='success'`、裸 JSON 三套判断逻辑，直接抵消 v1.37.1~11 十一个版本 L-1 统一的成果，且未来每次走查都会被重新标记为 L-1 违规。新功能必须"出生即合规"。
- **影响风险**：新接口**不触碰任何既有端点**，纯增量；但草案示例中前端代码需全部重写判断逻辑（见冲突 6）。

### 冲突 2【P0】路由注册：`register_project_routes(app)` → 违反路由统一装配约束

- **草案位置**：`handlers/project_routes.py` 内自带 `register_project_routes(app)` 批量注册。
- **现有代码事实**：`postman_api_tester/开发阅读文档.md:157` 明确 `report_server.py # 路由装配模块（38 条路由，仅装饰器 + 单行委托）`；实际代码 `report_server.py:360` 起全部为 `@app.route(...) + def xxx(): return _route_xxx()` 单行委托模式（当前 128 处 route 标记）。
- **改进内容**：删除 `register_project_routes`；新增路由（页面 4 条 + API 14 条）统一追加到 `report_server.py` 路由区，处理器函数放在 `handlers/project_routes.py`，report_server 中仅做装饰器 + 单行委托。
- **改进理由**：路由散注册会导致 `report_server_app.py` 与 `report_server.py` 双装配源，启动路径不可追溯，且违反约束 2.2 分层规则（handlers 不得持有 app 引用）。
- **影响风险**：`report_server.py` 是全局共享文件，**追加路由块不影响既有 38 条路由的行为**；风险仅在 import 顺序——project_routes 的模块级目录初始化需延迟（见冲突 4）。

### 冲突 3【P0】删除接口路径穿越：`PROJECTS_DIR / project_id` + `shutil.rmtree`

- **草案位置**：`delete_project` 直接拼接用户传入的 `project_id` 后 `shutil.rmtree`。
- **现有代码事实**：`utils/file_utils.py` 已提供 `sanitize_export_name(name)`（file_utils.py:17）；既有防护参考 `handlers/collection_routes.py:45` 使用 `(PROJECT_ROOT / "uploaded_collections").resolve()` + resolve 后包含性校验；`report_delete_service` 亦有同类校验。
- **改进内容**：
  1. `project_id` 服务端生成为 uuid4 短码（`str(uuid.uuid4())[:12]`，与 `ui_case_store.py:30` 一致），**不接受客户端传入 id 创建**；
  2. 所有以 `project_id` 定位路径的入口（get/update/delete/execute 共 4 类）先做白名单正则 `^[a-z0-9_-]{6,32}$` 校验，不合法直接 `json_error(400, "PRJ_400")`；
  3. 拼接后 `resolved = (PROJECTS_DIR / project_id).resolve()` 并断言 `resolved.is_relative_to(PROJECTS_DIR.resolve())`，防 `../` 穿越；
  4. `rmtree` 前校验 `resolved.is_dir() and (resolved / "project.json").exists()`，防止误删非项目目录。
- **改进理由**：这是草案中**唯一会物理删除数据的破坏性操作**，未 sanitize 时 `project_id=../../uploaded_collections` 可直接删掉现有上传目录——属 OWASP 路径遍历，必须修。
- **影响风险**：不修则威胁现有 `uploaded_collections/`、`ui_testing_cases/` 数据；修正后对现有功能零影响。

### 冲突 4【P0】目录硬编码 + `write_text` 直写 → 违反原子写与目录解析惯例

- **草案位置**：`Path(__file__).parent.parent.parent / "projects"` 模块级硬编码；`project.json` 用 `write_text` 直写。
- **现有代码事实**：`utils/file_utils.py:36` 提供 `atomic_write_json(path, data)`（临时文件 + replace，防写一半断电损坏）；M-12（v1.33.7 走查项）刚合并过 `_resolve_reports_dir` 双实现的教训——目录解析必须单一来源且支持环境变量覆盖（`collection_routes.py:45`、`report_server_app.py:77` 模式）。`ui_case_store.py:17` 的 `Path("ui_testing_cases")` 相对路径写法是历史遗留，**新代码不应效仿**。
- **改进内容**：
  1. 在 `config.py` 新增 `PROJECTS_DIR = _resolve_project_root() / "projects"` 与 `PROJECT_TEMPLATES_DIR`，支持环境变量 `PROJECTS_DIR` 覆盖；
  2. store 类构造函数接受 `projects_dir: Optional[Path] = None` 注入（便于单测 tmp_path）；
  3. 所有 JSON 落盘统一 `atomic_write_json`；
  4. store 内置 `threading.Lock`（参考 `ui_case_store.py:25`）。
- **改进理由**：避免再造"双实现目录解析"返工项；`write_text` 直写在并发保存/断电场景会留下半截 JSON 导致项目文件永久损坏。
- **影响风险**：config.py 为全局共享模块，仅**追加**两个常量与一次 `_env` 读取，不改任何既有值，风险极低。

### 冲突 5【P0】`callback_url` / 飞书 webhook → SSRF 与敏感信息风险

- **草案位置**：项目配置含用户可控 `callback_url`，执行完成/定时任务后由服务端 POST 回调，并内置飞书 webhook 通知。
- **现有代码事实**：现有对外发起请求的接口 `/re-request-api`、`/api/proxy-request`（`test_proxy_routes`，v1.37.10）已有 scheme 白名单校验（smoke 脚本断言非 http/https 返回 400）。注意边界：记忆约束"UI 代理链路禁止套用 `is_safe_url()`"仅针对 **UI 代理**（代理目标是用户浏览器要访问的站点）；脚手架 callback 是**服务端主动出站请求**，与 re-request 同类，应执行 SSRF 防护。
- **改进内容**：
  1. callback_url 仅允许 `http/https` scheme，服务端解析主机后拒绝指向 loopback/link-local/元数据地址（169.254.169.254）——复用/提取 `test_proxy_routes` 现有校验函数为公共工具，**禁止 import 后套用到 UI 代理链路**；
  2. webhook secret/token 不入库明文，字段存环境变量名（如 `FEISHU_WEBHOOK_URL_ENV`）而非 URL 本体，或至少经 `utils/security.py` 脱敏后再写日志（记忆约束 H-2 Cookie 日志脱敏同源）；
  3. 回调超时 ≤5s，失败仅记日志不重试阻塞执行链路。
- **改进理由**：服务端回调是本项目 SSRF 攻击面新增点；草案"每 5 分钟扫描 + 服务端 POST 任意 URL"等于给登录用户一个内网探测器。
- **影响风险**：定时扫描线程是**新增后台线程**，需按 `ui_execution_routes` 的线程管理模式注册优雅退出，否则影响进程关闭（现有 report_server 关停链路）。

### 冲突 6【P1】前端：`{% extends "base.html" %}` + Bootstrap + jQuery → 依赖不存在、栈不一致

- **草案位置**：4 个页面模板均 `extends base.html`，使用 Bootstrap5/jQuery/FontAwesome，`response.code === 'success'` 判断。
- **现有代码事实**：`templates/base.html` **不存在**（已核实 glob 无结果）；现有页面（`report_view.html`、`collection_editor.html`、`ui_testing_editor.html` 等）全部为**单文件原生 JS + Jinja2 `{% raw %}` 保护**风格，无外部 CSS 框架（记忆约束：纯 JS 模板必须 `{% raw %}` 防 `{{var}}` 被 Jinja2 吞）。
- **改进内容**：
  1. 4 个新模板按现有页面同款单文件风格实现，含 `{% raw %}` 包裹 JS；
  2. 前端统一 `const raw = await resp.json(); const data = raw.data || raw;`，错误回退链 `data.details || data.error || raw.message || 原文`；
  3. 不引入 Bootstrap/jQuery/FontAwesome CDN（离线环境安全，现有页面均无外链 CDN）。
- **改进理由**：草案前端代码**当前状态直接跑不起来**（base.html 缺失、CDN 可能不可达）；且两套响应判断逻辑无法维护。
- **影响风险**：模板为纯新增文件；若引入外链 CDN 会在离线/内网环境产生整页样式崩坏，故禁止。

### 冲突 7【P1】分页参数未走 clamp 工具

- **草案位置**：列表接口手工解析 `page/page_size`。
- **现有代码事实**：`utils/server_utils.py:19` `clamp_page` / `:28` `clamp_page_size` 已统一处理非法/越界分页（L-3 魔法数字常量化的产物）。
- **改进内容**：`/api/projects` 等分页端点必须调用 clamp 工具，页大小上限沿用现有常量。
- **改进理由**：重复实现分页是 M-1/M-2/M-12 反复消除的"双实现"反模式，新增即欠债。
- **影响风险**：无（纯复用）。

### 冲突 8【P1】功能开关默认 `True` → 违反新功能默认关闭惯例

- **草案位置**：`ENABLE_PROJECT_SCAFFOLD = True`。
- **现有代码事实**：`config.py` 中成熟功能默认 true（如 ENABLE_DATA_DRIVEN），但**新功能/有风险功能默认 false**：`ENABLE_REQUEST_RETRY=false`(:85)、`ENABLE_ASSERTIONS=false`(:283)、`ENABLE_CHECKPOINT_RECOVERY=false`(:305)、`ENABLE_CONCURRENT=false`(:462)、`ENABLE_PRE_REQUEST_SCRIPT=false`(:476)，全部走 `_env_bool` 读取。
- **改进内容**：`ENABLE_PROJECT_SCAFFOLD = _env_bool("ENABLE_PROJECT_SCAFFOLD", "false")`；关闭时 API 返回 `403 + PRJ_403`（参考 `report_result_routes` 的 `ENABLE_REPORT_ANALYTICS` 403 模式），页面路由返回提示页；导航入口按开关注显隐。
- **改进理由**：夜间自动升级体系要求"默认保持旧行为"，新功能开启引发回归时可 revert 合并提交即恢复原状（约束 2.1 豁免条件的精神）；6 周开发期内即使代码进 master，未开启即零行为变化。
- **影响风险**：`report_server.py` 的路由 import 在模块加载期执行——project_routes 顶部不得做目录 mkdir 等副作用（懒初始化），否则开关关闭也无法隔离故障域。

### 冲突 9【P1】版本号写 v1.37.x → 应为 MINOR `v1.38.0`

- **草案位置**：无版本规划章节。
- **现有代码/记忆事实**：版本规则（记忆"版本号同步约束"）：PATCH=修复/重构、**MINOR=新功能**、MAJOR=大改版。当前最新 v1.37.11（master 已合并推送 fa5453f）。脚手架是全新子系统（新页面、新接口、新目录）→ MINOR。
- **改进内容**：实施完成时 `postman_api_tester/__init__.py` bump 至 `1.38.0`，并同步 **6 份文档**（README、开发阅读文档、快速命令参考、操作手册、最终交付清单、优化清单）+ 5 项文档走查；提交前 `python -m pytest tests/ -q` + `python -m mypy postman_api_tester` 全过；`--no-ff` 合并，未确认不推 master。
- **改进理由**：跳段/错段会破坏"最新版本上开发"纪律（记忆"版本号不能跳段"）。
- **影响风险**：无代码影响，流程性要求。

### 冲突 10【P1】新文件缺 mypy files 登记与单测要求

- **草案位置**：无测试/类型检查章节；`execute_project` 为空 TODO。
- **现有代码事实**：`pyproject.toml` mypy files 逐文件登记（:15-29 可见 services 全列表）；每个 routes 文件有对应 `tests/test_*_routes.py`（Flask test_client + mock service 模式，参考 `tests/test_report_result_routes.py`）。记忆约束：删除/新增 handler 都要同步 pyproject.toml。
- **改进内容**：
  1. 新增 `handlers/project_routes.py`、`services/project_service.py`、`services/project_store.py` 登记进 mypy files；
  2. 单测：`test_project_routes.py`（CRUD + 开关关闭 403 + 非法 id 400 + 路径穿越 400）、`test_project_store.py`（原子写、并发锁、uuid 生成）；
  3. `execute_project` 不允许 TODO 交付：复用 `services/report_job_execution_service.py:277 enqueue_job_with_worker` 与 `report_job_submission_service.build_run_postman_job_params`(:23) 入队，状态查询直接走既有 `/api/run-postman-status/<job_id>`（**该端点按决策 1 保持原始格式，不改**）；
  4. 新增页面入口与接口冒烟脚本放入 `test_data/`（含 `raw.data || raw` 解包）。
- **改进理由**：mypy 门禁会直接 CI 失败；空 TODO 的 execute 会让"项目执行"成为断链功能。
- **影响风险**：复用任务队列意味着**共享 `_active_jobs`/worker 资源**，见第四节风险 R3。

### 冲突 11【P2】5 个 service 文件拆分过度

- **草案位置**：project_service / template_service / tracing_service / project_store / project_template_store 五文件。
- **现有代码/记忆事实**：记忆"避免过度抽象"——优先模块化复用，不做薄壳拆分；现有 store 均为单类单文件（`ui_case_store.py` 259 行含 CRUD+锁）。
- **改进内容**：收敛为 2 个文件——`project_store.py`（项目 JSON 存取 + 模板 JSON 存取，两个小类同文件）与 `project_service.py`（业务编排：校验、执行入队、统计）。tracing（xlsx 导出）若保留则并入 project_service 或独立 `project_tracing_service.py`，取决于第三节冲突 12 的结论。
- **改进理由**：模板 CRUD 与项目 CRUD 逻辑同构，拆 5 文件制造 3 次跨文件跳转；handler 层已天然隔离职责。
- **影响风险**：无（纯结构设计）。

### 冲突 12【P2】tracing.xlsx 依赖 openpyxl → 新依赖风险

- **草案位置**：追踪矩阵导出 xlsx；`requirements.txt` 已核实**无** openpyxl/pandas。
- **改进内容**（二选一，倾向前者）：
  1. **v2 首版仅 CSV 导出**（stdlib csv，零依赖），xlsx 需求验证后再评估引入 openpyxl；
  2. 若必须 xlsx：openpyxl 以**延迟导入 + 功能降级**方式接入（未安装时接口返回 400 `TRC_501` 提示装依赖），并登记 requirements.txt + README 依赖说明 + 记忆知识库。
- **改进理由**：新增第三方依赖影响所有部署环境（含离线 wheel 安装流程），须以最小依赖面起步。
- **影响风险**：直接影响 `pip install -r requirements.txt` 的既有环境，属对外契约变化，需版本说明确认。

### 3.2 接口契约（示例，其余同构）

```
GET /api/projects?page=1&page_size=20
  开关关 → json_error("项目功能未启用", 403, "PRJ_403")
  成功   → BaseHandler.json_response({"items": [...], "total": n, "page": p, "page_size": s})
  body:  {"code": 200, "message": "OK", "data": {...}, "timestamp": "..."}
异常映射: 统一 @handle_api_errors({ValueError: (400,"PRJ_400"),
          FileNotFoundError: (404,"PRJ_404"), PermissionError: (400,"PRJ_400")})
          （base_handler.py:255 装饰器，消除重复 try/except）
```

### 3.3 Collection 归属模型（草案未明确，v2 补充）

- 项目内 collection **实体存放于 `projects/<project_id>/collections/*.json`**，与 `uploaded_collections/`（执行临时中间文件，README:445 定位）**职责不同、互不迁移、互不删除**；
- 项目执行时由 project_service 将选定 collection 内容经 `build_run_postman_job_params` 转为既有一次任务的 collection JSON 入队，产物仍是**现有 report 体系**（报告中心可见），脚手架不复制一套报告存储。

## 五、风险规避与实施纪律

1. **模块隔离**：除 R1 两个共享文件为"纯追加"外，所有新逻辑封闭在 3 个新 py + 4 个新模板内；任何"顺手改现有文件"的诱惑均拒绝（分支隔离，只改进不破坏）。
2. **默认关闭**：`ENABLE_PROJECT_SCAFFOLD=false` 合入即零行为变化；灰度顺序：本地开 → test_data 冒烟 → 夜间任务验证 → 用户确认后再默认开启（单独 PATCH）。
3. **回退方案**：feature/auto-upgrade-YYYY-MM-DD 分支开发，`--no-ff` 合并；回滚 = `git revert -m 1 <合并提交>`，数据目录 `projects/` 未开启不产生，无数据迁移故 revert 即净。
4. **门禁**：每子项独立提交；提交前 `python -m pytest tests/ -q` + `python -m mypy postman_api_tester` 全过；合并推送前 6 文档版本号统一并做 5 项文档走查；汇报提交前 `git log` 核实真实 hash（2026-09-01 教训）。
5. **分期交付建议**（替代草案 6 周计划）：
   - 阶段 1：ProjectStore/ProjectService + project CRUD 接口 + 单测（无前端）
   - 阶段 2：模板库 + 从模板创建 + 前端项目页
   - 阶段 3：execute_project 入队打通 + 状态轮询复用
   - 阶段 4：统计/追踪（CSV）+ 操作手册/知识库 + v1.38.0 收口
