# 可视化编辑器断言能力实施方案（含全链路冲突/风险走查）

- **日期**: 2026-09-02
- **版本安排（用户已定）**: 在 v1.37.13 基础上按 PATCH 递增（v1.37.14 起），**不占用 v1.38.0**；UI 自愈（v1.38.0）与脚手架（v1.39.0）版本号不变，本功能先行合入 master 后自愈分支自然从新基线拉出。
- **状态**: 方案讨论——未改任何代码，待用户确认后实施。

---

## 一、走查结论（最重要，先推翻一个前提）

用户诉求是"给可视化编辑器增加断言编辑能力"。走查发现：**JSONPath 断言功能当前整条执行链路是断裂的（僵尸功能）**——只给编辑器加 UI 而不修链路，断言编辑了也不会生效。逐点证据（行号实证）：

| # | 断点 | 证据 | 现状 |
|---|---|---|---|
| B-1 | ad-hoc 前端→后端 | `adhoc_run.html:957` 发送 `payload.assertions_json`；全仓 `grep assertions_json --include=*.py` **零命中**；`normalize_adhoc_case`（collection_utils.py:588-599）字段表中无断言 | 前端输入被**静默丢弃** |
| B-2 | Collection→parser | `_parse_x_extensions`（parser.py:230-277）白名单仅 string/bool/dict/int 四类，**无 list 分支**；`x_assertions` 不会进 `extensions` | 文件里写了也丢 |
| B-3 | executor 读取 | `executor.py:742` `api.get("x_assertions")` 恒为 None → `_run_assertions` 恒空跑 | 引擎（13 操作符）从未被真实触发 |
| B-4 | 报告展示 | `result.assertion_results` 唯一消费者是 analytics"断言完整性评分"（report_analytics_service.py:240-241）；`report_view.html` 详情区**无断言结果块** | 即使断言生效，用户看不到失败明细 |
| B-5 | 文档口径 | 最终交付清单 :35、操作手册 :793 声称"断言失败标记 FAILED"已交付 | 与事实不符（疑似后续 handler/service 重构时丢失接线） |

**已就位、零改动的部分**（好消息）：
- 判定翻转逻辑：`_build_passed_result`（executor.py:250-255）`assertion_failed = any(not a.passed)` → FAILED——B-1~B-3 修通后自动生效；
- 断言引擎本体：`assertions.py` 13 操作符（eq/ne/gt/lt/gte/lte/contains/regex/length_eq/type/schema/exists/not_exists），jsonpath-ng 为有效依赖；
- 编辑器 UI 模式：页签制（General/Headers/Params/Body/Pre-request/x_extract），`renderExtractTab`（collection_editor.html:1596）是现成的"三列规则行增删改"先例；
- 编辑器执行链：Send/执行 走同一 executor，无需新端点。

## 二、与现有功能的冲突分析（用户问"是否有冲突"）

| 项 | 结论 | 依据 |
|---|---|---|

| 与自愈排期时序 | 正向：本方案先合 master，自愈 S0 冻结 BASE 时自然基于新基线；自愈方案未硬编码行号锚点外的版本号假设（v4 S0 动态取 BASE） | — |
| 与 L-1 响应统一 | **无冲突**：不新增端点；编辑器 parse/save/send、job 提交等既有端点的响应结构不变（断言数据只存在于 collection JSON 载荷体内） | collection_editor_routes 已于 v1.37.8 包装完成 |
| 与约束 3.10.5 稳定端点 | 不触碰 | — |
| 与 ENABLE_ASSERTIONS（v1.37.12） | 语义保持：该开关仍只管 UI 显隐，**执行链仍不消费它**（修链后也不引入执行侧消费，维持 v1.37.12 文档承诺）；编辑器断言页签同样受它门控（与 ad-hoc 一致） | config.py:283 注释 |
| 与结果自动判定（v1.3.3） | 无冲突且顺序不变：executor 先 `_evaluate_judgment`（errCode/message）判 FAILED，passed 分支才跑断言（executor.py:463-472）——判定与断言是两级，叠加语义为"判定过 && 断言过 = PASSED" | 行号实证 |
| 与变量替换 | 已知边界非冲突：`variable_substitution.py:110-120` 跳过列表含 `x_assertions`，即断言 path/expected **不支持 `{{变量}}` 替换**。首期维持现状（见 R-5） | — |
| 与数据驱动/重试/导出/checkpoint | 无交互（断言只是 request 内一个 list 字段，随结果行记录）；重试复用 executor，自动带上断言 | — |

## 三、风险清单与解决方案

| # | 风险 | 级 | 解决方案 |
|---|---|---|---|
| R-1 | **存量集合行为翻转**：某集合历史上带 `x_assertions`（B-2 曾静默忽略），修复后断言真正执行，个别用例可能 PASSED→FAILED | P1 | 不引入新开关（避免与 v1.37.12 语义自相矛盾）。发布说明/changelog 显著标注"断言自 v1.37.14 起真正生效"；验收含"无断言集合执行结果逐字段不变"回归用例（F-4） |
| R-2 | 脏数据入引擎：外部文件的 x_assertions 可能是 dict/字符串/含非法 op → evaluate 崩溃 | P1 | 统一归一化函数 `normalize_assertion_rules(raw) -> List[Dict]`：仅保留 `list[dict]` 中 `op ∈ SUPPORTED_OPS` 且含 `path` 键的规则，其余丢弃 + `logger.warning`（带 item 定位）。parser（B-2）、ad-hoc（B-1）、编辑器（F-3）**三处共用同一函数**（放 `assertions.py`，避免三份实现再腐化） |
| R-3 | 编辑器往返丢字段：service parse/build 不认 x_assertions，编辑一次抹掉用户断言（现状 bug） | P0（功能正确性） | parse 提取（:155 区，经 R-2 归一化）、build 透传（:324 区）；保存/导出与导入执行链路口径一致 |
| R-4 | 前端 innerHTML 渲染 path/expected/op 引发存储型 XSS | P1 | 断言页签全部值经既有 `escapeAttr/escapeHtml`（extract 页签:1604 先例）；report_view 断言结果块同理（expected/actual 是用户可控数据）；验收 F-6 用 `<img src=x onerror=...>` 样例断言 |
| R-5 | 断言 expected 想引用 `{{变量}}` 的用户预期不满足 | P3 | 首期明确不支持（跳过列表维持），文档在手册 5.断言节写"已知边界"；有需求再另案 |
| R-6 | Jinja2 吞模板字面量：新 JS 若含 `{{` 会被 Jinja 解析 | P2 | 断言占位符文案避开 `{{`（示例用 `$.data.id`）；确需时该 JS 块包 `{% raw %}`（记忆先例）；实施后 grep 双花括号自查 |
| R-7 | B-4 不修则用户仍"看不见"断言失败原因，误以为工具坏了 | P1 | 纳入首期：report_view 详情区新增断言结果小表（path/op/expected/actual/passed/message），仅当 `assertion_results` 非空渲染；旧报告无此字段 → `.get` 空短路天然兼容 |
| R-8 | 与自愈实施期撞车：若本功能拖到自愈分支开出来后才合入 | P2 | 排期约束：本方案 3 步提交在自愈分支拉出**之前**全部合入 master（见实施步骤）；若来不及，自愈分支 rebase 时本方案文件与其白名单零交集，冲突概率≈0 |
| R-9 | 重试失败用例（retry-failures）对新"断言 FAILED"的重跑放大执行成本 | P3 | 接受：语义正确（FAILED 本就该重试）；零改动 |
| R-10 | JUnit 导出不体现断言失败明细（仅整体 FAILED 状态） | P3 | 停车场：另案。状态位本身由 executor 结果驱动，断言失败已能传导为 testcase failure，不阻塞首期 |

## 四、实施范围（最小闭环，3 步 PATCH 提交）

### Step 1（v1.37.14）执行链修复——B-1/B-2
- `assertions.py`：新增 `normalize_assertion_rules(raw)`（R-2 契约：op 白名单 + path 必填 + list[dict] 过滤 + warning 日志）。
- `parser.py::_parse_x_extensions`：新增 list 分支 `x_assertions`（调 normalize）。
- `collection_utils.py`：`normalize_adhoc_case` 提取 `raw.get("assertions_json")`（payload 键名即前端 :957 所发）→ result 字典；`build_adhoc_collection` 写入 `request_obj["x_assertions"]`（非空才写）。
- 测试：parser 透传正反例 / ad-hoc 端到端（临时 collection 落盘 JSON 断字段存在）/ normalize 脏数据 6 例；全量 pytest + mypy。
- 验证命令：`python -m postman_api_tester.postman_api_tester` 跑带断言样例集合，details.json 出现 `assertion_results`，失败样例翻 FAILED。

### Step 2（v1.37.15）编辑器能力——R-3/R-4/R-6
- `services/collection_editor_service.py`：parse（:155 区）提取 `x_assertions`（经 normalize）、build（:324 区）透传。
- `templates/collection_editor.html`：新增"断言"页签（tabLabels:1246 + 分派 :1386/:1396 + `renderAssertionTab` 抄 extract 模式：path 文本框 / op 下拉 13 项 / expected 文本框，exists/not_exists 时 expected 置灰；增删改 + 全值 escape）。页签可见性随 `enable_assertions` 门控（模板既有传参，零后端路由改动）。
- 测试：service 往返测试（含断言 collection parse→build 不丢）；手工冒烟（编辑器配断言→执行→FAILED）。

### Step 3（v1.37.16）报告展示——B-4/R-7
- `templates/report_view.html`（及 html_reporter 对应模板，若有静态报告版）详情区断言结果小表；`最终交付清单.md` :35、`操作手册.md` 断言节改写为真实行为 + 已知边界（R-5）；changelog 标注 R-1 行为翻转提示。
- 测试：details.json 注入 assertion_results 渲染冒烟；旧报告（无字段）不报错。

### 非目标（停车场，另案）
- Send 单接口即时断言调试评估；`$status`/`$header`/`$response_time` 断言维度扩展；JUnit 断言明细；expected 变量替换。

## 六、实施偏差回写（实施期实证，2026-09-02）

1. **Step 1（v1.37.14）注入点**：方案原写"`normalize_adhoc_case` 提取 `raw.get('assertions_json')`"。实证 `assertions_json` 位于 **payload 顶层**（adhoc_run.html:957）而非单条 case 内，故归一化与注入改在 `job_routes.api_run_ad_hoc_tests` 完成（normalized_cases 后循环写入 `case["x_assertions"]`），`collection_utils` 仅负责 `build_adhoc_collection` 写入段（非空才写）。行为等价，链路更短。
2. **Step 2（v1.37.15）页签门控**：方案原写"模板既有传参，零后端路由改动"。实证 `page_routes.collection_editor_page`（:110）**并未**传 `enable_assertions`，已补 +1 kwarg；且 `collection_editor.html` 整体包裹在 `{% raw %}` 中，Jinja 门控需 `{% endraw %}...{% raw %}` 夹取（已实现并用渲染测试验证开/关/未传参三态）。expected 值经前端 `JSON.parse` 尝试解析以保 JSON 字面量类型（数字/布尔/对象），失败按字符串。
3. **Step 3（v1.37.16）展示范围**：`build_result_detail_payload`（report_results_service.py）详情白名单原不含断言字段，已补 `assertion_results`/`assertion_engine_error` 透传（旧报告缺省空）。静态报告（`core/html_reporter.py`）**不加**结构化断言表：executor 已将断言失败明细聚合进 `message`（"断言失败: …"），行表 message 列可见，结构化明细统一在动态报告 `report_view.html` 详情弹窗渲染（新增 `renderAssertionResultsHtml`，非空才渲染、全值转义）。

## 七、结论

功能本身与现有系统**无结构性冲突**；真正的价值在走查发现的链路断裂（B-1~B-5）——若按原始诉求只加编辑器 UI，将交付一个"能编辑、不生效"的假功能。方案按 3 个 PATCH 步（1.37.14/15/16）修复 + 增能 + 展示收口，全程不触碰自愈改动面白名单，自愈 v1.38.0 排期与版本号不受影响。
