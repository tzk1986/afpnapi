## 一、V5-1【P0】门控条件含死开关——照 v3 实施自愈将永远不可用

- **走查证据**：`grep -rn "UI_HEADLESS_ENABLED" --include=*.py` 全仓**仅 config.py:506-507 定义处命中，零消费者**。无头模式的真实启用路径是请求体 `mode`（`ui_execution_routes.py:185`：`mode = payload.get("mode", settings.get("default_mode", "browser_replay"))`），与这个 env 开关无关——它是历史遗留死配置。
- **v3 的错误**：§二 生效门控与 §四-M2d 钩子条件都写了 `UI_SELF_HEALING_ENABLED and UI_HEADLESS_ENABLED`。因 Python `and` 短路，`UI_HEADLESS_ENABLED=False`（默认且无人设置）→ **钩子永远短路，用户设 `UI_SELF_HEALING_ENABLED=true` 也毫无效果**。
- **修正（覆盖 v3 §二/§四-M2d、v4 S1.4）**：门控链定稿为
  ```
  UI_SELF_HEALING_ENABLED && self._healing_active && not 熔断 && not 去重命中
  ```
  ① 删除 `UI_HEADLESS_ENABLED` 条件；② "仅无头"由**架构保证**（engine 只被 headless worker 进程使用，见 routes:260/:328 `mode=="headless"` 分支才 `start_headless`），无需 env 冗余门控；`ui_login_routes` 复用引擎的路径由 `_healing_active=False` 覆盖（N-6）。
- **影响风险**：门控只剩一个 env——误开面收窄为"显式设 UI_SELF_HEALING_ENABLED=true"，符合"运维级开关"语义（N-10 初衷不变）。
- **规避**：S1.4 单测 F-1 拆两例：env False → 钩子零执行；env True + 无 UI_HEADLESS_ENABLED 设置 → 钩子正常执行（专防本条回归）。grep 断言新增 **⑩：引擎本次 diff 中 `UI_HEADLESS_ENABLED` 0 命中**。
- **死开关本体**：记入附录 C PP 清单（`UI_HEADLESS_ENABLED` 定义未消费，违反"定义即消费"），**本方案不修**，转后续夜间任务评估接线或删除。

## 二、V5-2【P1】主循环无 fail-fast——熔断计数语义必须钉死为"尝试数"

- **走查证据**：主循环 :341-845 的 `break` 仅三处（cancel :342-343、new_tab 前置校验 :707、post-check 终止 :841/:845），**普通步骤失败不终止后续执行**（steps_failed 计数继续跑完）。推论：选择器体系整体腐化的用例，**每个坏步骤都会各进一次钩子**。
- **v3/v4 含糊处**：熔断 `UI_HEALING_MAX_PER_CASE` 未定义计数对象；若实现者数"成功数"，被 reject 的探测会无限增长（每步 count 探测 + 全策略链白跑）。
- **定稿（覆盖 v3 M8"熔断计数"、v4 S1.5）**：
  - `_heal_attempts`：**进入策略链的步数**（含 reject/未命中），达上限后钩子整体短路（探针也不再跑，仅剩 `_heal_once` 去重前的判断成本）；`capped` 事件在此刻发一次。
  - `_healed_steps`：仅成功自愈步数 → 写入 summary `healed_steps`（见 V5-4）。
  - 两计数分离，禁止一个计数器兼职。
- **新增验收 F-15**：构造 10 个连续失败交互步骤 + `UI_HEALING_MAX_PER_CASE=5` → `classify_failure` 调用计数 ≤5（monkeypatch），第 6 步起零探测零策略；事件含一条 `self_healing.capped`。

## 三、V5-3【P1】context 设置点收敛到循环头一处（v3 有竞态隐患）

- **走查证据**：v3 §四-M2c 把 `_current_step_index/_current_action` 设在"三个 `_execute_step*` 调用点之前"（:721/:754/:758）——但循环头 :346 已有归一化变量 `action = step.get("action", "").lower()`，且 :343 前还有 new_tab 分支中途 `continue/break` 路径，三点分散赋值一旦漏点即"串步"（heal 记到错误 index/action）。
- **定稿（覆盖 v3 M2c）**：
  ```python
  # :346 之后（循环头，唯一插入点）：
  self._current_step_index = i
  self._current_action = action        # 复用循环变量，不重读 step（None/null action 防崩）
  self._current_step = step
  self._last_heal = None
  ```
  回写点钉死一处：`:763-764`（`step_result["index"]=i; duration` 段后、`on_step_complete`(:780) 与 post-check(:788+) 之前）——heal 字段在持久化与状态翻转之前落位，`healed_then_failed`（post-check 翻转）语义自动成立。
- **规避**：F-1 系列补一例：new_tab 前置失败分支（:707 break）不留脏 `_last_heal`（循环头已重置，天然成立，单测锁死）。

## 五、修订后的生效门控与计数（唯一真源，替换 v3 §二图下方与 §四-M2d）

```
触发链（全部短路判断，顺序固定）：
UI_SELF_HEALING_ENABLED            # env，默认 false（V5-1 后不再叠 UI_HEADLESS_ENABLED）
&& self._healing_active            # execute()=True / execute_login_config()=False（N-6）
&& self._heal_attempts < UI_HEALING_MAX_PER_CASE   # 熔断按"尝试数"（V5-2）
&& i not in self._heal_once        # 同步去重（T-3）
&& self._current_action 非 assert 前缀              # R-7 豁免（读 V5-3 循环头变量）
→ classify_failure == not_found    # N-4 分型（unknown/exists 拒）
→ try_heal 四级（N-5 映射；count==1 先于 is_visible，V5-7）
→ 置信度 ≥ UI_HEALING_CONFIDENCE → 采纳：_last_heal 置位、_healed_steps+1、
   _healed 截图（N-8）、self_healing.healed 事件
  未采纳/被拒 → _heal_attempts 已计入、self_healing.rejected 事件、原异常照抛
（_heal_attempts 在进入 classify_failure 前 +1；任何拒绝路径不回退计数）
```
